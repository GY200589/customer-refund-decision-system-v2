## 任务一的核心目标

任务一的定位非常明确：在编写任何业务代码之前，把需求和技术方案彻底敲死。工单原文明确要求“在需求文档定稿前，不允许进入编码”，这是一个硬性红线。

用一句话概括：任务一产出的是项目的“设计蓝图”，后续的代码、测试、部署全部基于这张蓝图展开。

## 任务一具体要求拆解

### 1. 三方对齐机制（Human + AI-A + AI-B）

这是任务一最有特色的环节，也是工单反复强调的“消除认知偏差”的关键步骤。具体分三步走：

| 步骤 | 谁参与 | 做什么 |
| :--- | :--- | :--- |
| 步骤1：启动逆向澄清 | 学生 → AI-A(Gemini) + AI-B(Cursor) | 把原始需求分别发给两个AI，要求他们用自己的话转述需求，列出模糊点、冲突点和异常边界，并向学生抛出决策问题 |
| 步骤2：三方对齐与多轮互评 | AI-A ↔ AI-B 互评，学生裁决 | 将AI-A的方案发给AI-B评审，将AI-B的方案发给AI-A评审，交叉验证，消除认知偏差 |
| 步骤3：文档先行 | 学生主导 | 输出最终《需求与技术方案说明书》，定稿前不得编码 |

三方职责划分非常清晰：

- 人类（学生）：下达需求、裁决冲突、圈定MVP范围
- AI-A（分析助手，如Gemini）：逆向转述需求、挖掘业务边界（如OCR置信度过低、舆情风控超时如何处理）、设计异步解耦方案
- AI-B（编程助手，如Cursor）：评估技术栈可行性、设计状态机无状态方案、设计分布式锁防重方案

### 2. 输出物要求

任务一必须交付三份文档：

① 《需求分析与WBS拆解文档》

- 业务背景、MVP功能范围
- 异常场景处理策略（如“如果OCR识别超时，则返回XXX”）
- 1人1周的任务拆解表

② 《三方需求互评与对齐记录》

- 记录三方关于“状态挂起、超时解耦、高并发防重”等核心技术决策的讨论
- 验收标准要求：必须体现AI提出的至少3个业务/工程架构异常点，且有学生给出的明确技术裁决

③ 《核心技术架构深度剖析手册》（自述文档/脑图）

- 必须自己整理，不能用AI生成，这是验收红线
- 覆盖四大板块：

| 板块 | 核心内容 |
| :--- | :--- |
| 架构力 | LangGraph无状态服务设计（Redis Checkpointer）、FastAPI+Redis Streams+Worker异步长任务处理流向 |
| AI工程化 | 四大Agent（Intake/Evidence/Fraud/Sentiment）职责划分、大模型Output Parse失败时的Fallback机制 |
| 算法与数据处理 | PaddleOCR置信度阈值路由设计、基于最小活跃任务数的工单派发算法 |
| 工程防御 | 幂等键设计公式、Redis SETNX分布式排他锁方案 |

## 任务一实现了什么功能

注意：任务一不写代码，产出全是文档。它实现的是以下功能：

- 需求澄清：把工单里模糊的描述（如“OCR识别”、“舆情风控”）转化为无歧义的功能规格
- 异常场景覆盖：明确“如果A发生，系统应该返回B”的所有边界条件
- 技术方案锁定：确认LangGraph+FastAPI+Redis+PostgreSQL的技术栈，定下状态机持久化方案、分布式锁方案、异步任务方案
- 工作量评估：输出1人1周的WBS拆解，让后续开发有据可依
- 知识内化：通过自述手册，学生必须自己理解并复述四大技术板块，防止“AI写了但我没懂”

## 面试中如何讲任务一

可以这样组织话术：

> “任务一我花了1.5人日，核心是先设计后编码。我用了三方对齐机制——让Gemini做业务分析，Cursor做技术评估，我来做最终决策。比如在讨论‘OCR识别超时怎么办’时，Gemini建议挂起转人工，Cursor建议异步队列解耦，我拍板两个都要——于是就有了后续的Redis Streams异步方案和Human-in-the-loop兜底机制。最终产出了三份文档，其中《核心技术架构剖析手册》是我自己写的，从LangGraph状态机到分布式锁都梳理了一遍。验收时要求AI必须提出至少3个异常点并有我的裁决记录，我实际收集了5个，最典型的是‘大模型Output Parse失败时的Fallback’——我决定用正则兜底+记录原始输出供人工复核。”

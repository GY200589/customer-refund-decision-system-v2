## §0 一页速览（电梯演讲 + 核心数据卡）

### 0.1 一句话定位

> "一个基于 **LangGraph 多 Agent 编排**的客诉退赔决策系统：**5 个 Agent 串行联动 + 确定性规则引擎 + 人工断点兜底**，让退款决策'能自动的不手动、该人工的不放过'——**低风险秒退、高风险挂起**，全程可审计、可复算、可压测。"

### 0.2 解决什么问题

传统电商退款决策存在**三个致命短板**：① **看不懂图片凭证**——用户上传的付款截图、物流单号靠肉眼核实，无法自动化；② **识别不了舆情风险**——`if-else` 规则无法感知用户近期的投诉倾向、恶意话术和外部舆情事件；③ **易被"羊毛党"钻空子**——欺诈行为缺乏交叉验证，高并发下人工审核形同虚设。结果就是**人工审核压力大、资损风险高、决策不可追溯**。

本项目把"低风险自动退、高风险人工兜底"落地成一套**端到端、可容器化部署、可压测自证**的全栈系统——**LLM 不碰钱、Agent 做判断、规则做裁决、人工守底线**。

### 0.3 技术栈一行

**FastAPI + LangGraph + PostgreSQL + Redis**（后端）· **React 18 + TS + AntD v5**（前端）· **PaddleOCR + Ollama/Qwen2.5**（本地模型）· **Docker Compose + Locust**（部署/压测）。

### 0.4 核心数据卡（⚠️ 数字要如实，这是防被戳穿的底线）

| 指标 | 数值 | 口径 |
| :--- | :--- | :--- |
| 后端测试 | **47/47 pytest 通过** + 端到端 **17/17 断言** | 当前仓库真实运行 |
| 压测（功能验证） | **20 并发、259 请求、0 失败、平均 61ms、吞吐 13 req/s** | Locust 单机实测 |
| 建案接口 | 平均 **60ms** | 异步解耦收益 |
| 登录接口 | 平均 **340ms** | bcrypt 刻意昂贵（防爆破） |
| 高并发（200/500/1000 QPS） | **工单验收分档，非本机实测** | 已有瓶颈分析与扩容预案 |

> **诚实原则（面试关键）**：被问"极限 QPS 多少"，答"我做了 20 并发功能验证 0 失败 + 完整的瓶颈分析与扩容预案"，比虚报数字可信十倍。

## §1 系统架构（一张图讲清）

```
用户 → React 前端(antd)
         │ /api
         ▼
   FastAPI（JWT鉴权 / RBAC / 幂等 / 锁）── 写库 + 投递 Redis Stream ── 立即返回 202
         │
         ▼
   Redis Stream (refund:stream)
         │ xreadgroup（消费者组，XACK + DLQ）
         ▼
   Worker ──▶ LangGraph 8 节点工作流：
              intake → evidence(OCR) → fraud → sentiment → decision
                → human_review(interrupt 挂起) ── 主管 resume ──
                    ├─ APPROVE → execute_refund（退款执行）
                    └─ REJECT  → reject（驳回）
         │
         ▼
   PostgreSQL（案件/审计/幂等记录 = 事实源）   Redis（checkpoint/Stream/锁/事件 = 进度）
```

**一句话**：**内存里是"进度"，数据库里是"事实"**——Redis checkpoint 管断点续跑，PG 状态机管业务不悬空、可审计。

## §2 8 个 Agent 职责 + 是否碰大模型

| Agent | 职责 | 碰大模型？ |
| :--- | :--- | :--- |
| IntakeAgent 受理校验 | 订单号/金额/字段校验 | ❌ 确定性 |
| EvidenceAgent 取证 | OCR 提取凭证文字 + 置信度 | ❌ 调 PaddleOCR |
| FraudAgent 欺诈检测 | 欺诈风险 0–100 打分 | ✅ LLM 辅助（输出结构化分数） |
| SentimentAgent 舆情分析 | 情绪分 + LOW/MEDIUM/HIGH 分级 | ✅ LLM 辅助 |
| DecisionPolicy 决策 | 算 APPROVE/REJECT/HUMAN_REVIEW | ❌ **纯规则** |
| HumanReview 人工审批 | `interrupt()` 挂起等主管 | ❌ |
| ExecuteRefund 退款执行 | 幂等退款、流转 COMPLETED | ❌ |
| Reject 驳回 | 流转 REJECTED 终态 | ❌ |

**核心原则一句话**：**「LLM 不碰钱」** —— 金额走整数分、裁决走确定性规则，大模型只输出风险评分，评分异常一律转人工。

## §3 决策规则引擎（确定性 if/else，可复算可审计）

从上往下短路判断：

| 规则 | 阈值 | 处置 |
| :--- | :--- | :--- |
| 证据不足（无凭证） | — | 转人工 |
| 金额 > 阈值 | 默认 300 元 = 30000 分 | 转人工 |
| 命中高风险舆情信号 | 监管转办/诉讼/媒体曝光/隐私泄露/群体投诉 | 转人工 |
| OCR 置信度 < 阈值 | 0.80 | 转人工 |
| 欺诈分 ≥ 拒绝阈值 | 80 | **直接拒绝** |
| 欺诈分 ≥ 复核阈值 | 50 | 转人工 |
| 舆情等级 = HIGH | — | 转人工 |
| 其余 | — | **自动批准** |

> 决策**不调用 LLM**，所以幻觉最坏结果 = "多转一单人工"，绝不会"错误放款"。

## §4 七个「为什么」（设计决策 · 面试从任何一句"为什么"切入都能答）

| # | 为什么 | 核心答案（why + how） |
| :--- | :--- | :--- |
| D1 | 金额用整数"分"不是 float？ | float 有二进制误差（0.1+0.2≠0.3），资金累加会账实不符；全链路 `amount_cent` 整数分，仅展示层转"元" |
| D2 | 决策交给确定性规则而非 LLM？ | LLM 有幻觉、不可复现；红线"模型只能辅助决策"，裁决走阈值表，保证可复算可解释可审计 |
| D3 | 选 LangGraph 而非手写状态机？ | 需要"挂起→恢复"，LangGraph 内置 Checkpointer + `interrupt()` 开箱即用，省去自研持久化/恢复/重入幂等 |
| D4 | API 只投递消息就返回？ | 大模型推理 2~5s，同步跑会阻塞 Web 线程池、QPS 崩到个位数；写库+投 Stream 即返 202，Worker 异步消费 |
| D5 | 幂等+分布式锁+乐观锁三层一起上？ | 三者防的是**不同层风险**：重放 / 并发抢占 / 丢失更新，单用任一都有盲区 |
| D6 | 断点续跑而非从头重跑？ | 重跑会重复调大模型（浪费+结果漂移）且中间态丢失；interrupt 挂起 + resume 原地继续 |
| D7 | OCR/LLM 本地化而非调云 API？ | 客诉含隐私不能出域 + 逐笔调云成本不可控；本地 PaddleOCR + Ollama，零 API 成本 |

## §5 四大核心亮点（STAR 拆解 · 背到能脱稿）

### P1 亮点：异步解耦，长任务不阻塞接口

- **S**：大模型推理 2~5s，同步执行 QPS 崩到个位数。
- **T**：请求秒级返回、任务不丢。
- **A**：API 只"写库 + 投递 Redis Stream"即返 202；Worker 用**消费者组**异步消费，`XACK` 至少一次投递 + DLQ 兜底。
- **R**：建案接口实测 **60ms**；Worker 崩溃未 ACK 的消息可重启续跑，支持多 Worker 水平扩容。

### P2 亮点：防大模型幻觉 —— 「LLM 不碰钱」

- **S**：测试时风控 Agent 把"正常退货"误判成"高危欺诈"。
- **T**：不牺牲自动化前提下防幻觉、守资损红线。
- **A**：① 决策交给确定性规则而非 LLM；② 置信度分级路由（OCR<0.80 转人工）；③ 模型异常/低置信**一律转人工、绝不自动通过**。
- **R**：幻觉被收敛到"最多多转一单人工"，绝不错误放款。

### P3 亮点：人机协作断点续跑不丢状态

- **S**：高风险必须人工接管，但挂起后状态丢了案件就"悬空"。
- **T**：AI 处理常规案件，高风险原地挂起、审批后从断点继续。
- **A**：`human_review` 节点 `interrupt()` 挂起 → 图上下文序列化到 **Redis checkpointer**；`thread_id = case_id` 对齐；主管审批用 `Command(resume=...)` 跨进程恢复；业务状态**同时落 PG**（SUSPENDED + ReviewTask + AuditLog）。
- **R**：跨 API/Worker 进程断点续跑；checkpoint 丢了也能从 DB 重建、不悬空。

### P4 亮点：三重防重复退款

- **S**：重复提交、两个主管并发审批都可能重复扣款。
- **T**：同一请求只处理一次、并发审批只一个成功。
- **A**：① `X-Idempotency-Key` + 请求体哈希（同键不同体报 422）；② Redis `SET NX PX` 分布式锁 + **Lua 校验 token 释放**；③ 乐观锁 `UPDATE ... WHERE version=?`，行数为 0 抛 `ConcurrencyConflict`。
- **R**：20 并发压测 0 重复退款、0 状态覆盖。

### P5 亮点：本地化降本 + Provider 可插拔

- **A**：OCR 用 PaddleOCR（本地 PP-OCRv5）、风控/舆情用 Ollama + Qwen2.5；所有模型抽成 `Provider` 抽象基类，`settings.*_provider`（mock/paddle/ollama）一键切换。
- **R**：数据不出域、零 API 成本；演示确定性可复现、生产无缝替换真模型。

## §6 踩坑与修复（真实案例 · 痛点 STAR）

> 面试官爱问"你踩过什么坑 / 怎么排查难复现问题"，下面每个都能讲成 STAR。

### P6【最值得讲】人工审批偶发 500（checkpointer 静默回退）

- **S**：审批接口偶发 500 `KeyError: 'case_id'`，重启后又正常，极难复现。
- **A**：看日志 `Redis checkpointer init failed` → 定位 redis-stack 冷启动 `BusyLoadingError` 触发 checkpointer **静默回退内存** → API 用内存、Worker 用 Redis，resume 找不到 checkpoint 从 intake 重跑。
- **修复**：失败先重试 10 次 + 退避，生产 **fail-fast**（抛错让容器重启），仅 test 环境允许回退内存。
- **R/教训**：跨进程共享状态时"静默降级 = 状态分裂"，降级边界必须显式。

### P7 并发建表竞态（UniqueViolation）

- **现象**：`uvicorn --workers 4` 启动偶发 `UniqueViolation: pg_type_typname_nsp_index`。
- **根因/修复**：`create_all` 的 check-then-create 在 4 进程并发下撞唯一索引；捕获 `IntegrityError` 重试自愈。
- **教训**：DDL 在多实例部署天然有竞态，生产应上 Alembic 迁移。

### P8 前端"黄灯闪烁"永不触发（props 契约）

- **根因/修复**：组件重构后调用方传 `terminal`、组件读 `status`，`SUSPENDED` 恒 false；对齐 props 契约 + 补图例 + 重建镜像。
- **教训**：组件契约靠 `tsc` 强类型在编译期强制，杜绝"静默 undefined"。

### P9 AI 生成代码的 7 个边界小坑（AI 代码审查经验）

| 坑 | 根因 | 修复 |
| :--- | :--- | :--- |
| `langgraph-checkpoint-redis>=2.0.0` 装不上 | 臆造版本号（实际仅 0.5.1） | 先 `pip index versions` 查真实版本 |
| `RedisSaver.from_conn_string` 报错 | 返回上下文管理器而非实例 | 改 `RedisSaver(redis_url=...)` + `setup()` |
| resume 报 ConcurrencyConflict | interrupt 恢复会**重跑当前节点** | 节点改幂等，先查状态再流转 |
| 测试跨会话污染 | 幂等记录残留命中旧 case_id | fixture 里 `drop_all` + `create_all` |
| checkpoint 报 `unknown command 'JSON.SET'` | 镜像缺 RedisJSON/RediSearch | 换 `redis/redis-stack-server` 且不覆盖 command |
| `module 'app.agents' has no attribute 'intake'` | `__init__.py` 空文件未导出 | 显式 `from . import intake, ...` |
| `No module named 'app.infrastructure.config'` | 相对导入层级写错 | 点数 = 向上跳的层级 |

**一句话教训**：AI 写代码要"引依赖查版本、调库先看签名、interrupt 节点必幂等、集成测试必隔离状态"。

## §7 高频面试题速答（2~3 句一题）

- **Q1 为什么金额用整数分？** 资金操作，float 有二进制误差会账实不符；全链路 `amount_cent` 整数分，仅展示层转"元"。
- **Q2 怎么保证不重复退款？** 三重：幂等键（防重放）+ Redis 分布式锁（防并发抢占）+ 乐观锁 version（防丢失更新）。
- **Q3 多 Agent 怎么编排和断点续跑？** LangGraph `StateGraph` 8 节点 + 条件边；`human_review` 用 `interrupt()` 挂起，checkpoint 持久化 Redis，`thread_id=case_id`，审批用 `Command(resume)` 原地恢复。
- **Q4 模型给高风险，直接拒绝还是转人工？** 分级：fraud≥80 拒绝；fraud≥50、金额超阈、OCR 低、舆情 HIGH、模型异常全转人工。原则"模型绝不自动通过"。
- **Q5 为什么确定性 Mock + 真模型接口？** 测试要可复现、无外部依赖，生产要真实能力；Provider 抽象层 + 开关，两全其美。
- **Q6 为什么选 Redis Streams 而非 List？** Stream 原生支持消费者组（水平扩容）、`XACK` 至少一次投递、DLQ 兜底，适合"不能丢不能重复"的订单场景。
- **Q7 乐观锁 vs 悲观锁怎么选？** 审批是低冲突场景，乐观锁无锁开销、吞吐高；配合分布式锁兼顾性能与正确性。
- **Q8 API 和 Worker 怎么共享工作流状态？** 共用同一个 Redis checkpointer，`thread_id=case_id`，Worker 跑到 interrupt 落 Redis，API 用同 thread_id 的 resume 恢复。
- **Q9 checkpoint 服务不可用怎么降级？** 先重试 10 次 + 退避；仍失败，test 回退 MemorySaver，**生产 fail-fast**，绝不静默回退内存（会状态分裂）。
- **Q10 人工介入节点怎么不丢状态？** 双写：Redis checkpoint（进度）+ PG 状态机（事实）；DB 是事实源，checkpoint 丢了也能重建。
- **Q11 LLM 有延迟和幻觉，怎么保证高精度高性能？** 精度靠"LLM 不碰钱"（金额整数分 + 裁决确定性规则 + 输出结构化置信度兜底）；性能靠异步解耦 + Provider 分层 + 失败快速转人工。
- **Q12 金额怎么算高精度？** 金额从不经过 LLM，从入参整数分全链路确定性代码流转，精度=整数运算精度，与模型无关。

## §9 需求方法论：三方对齐（任务一的独特亮点）

- **背景**：工单红线"定稿前禁止编码"，需求模糊（"OCR""舆情风控"）。
- **做法**：① Gemini(业务分析) 与 Cursor(技术评估) 各自**逆向转述**需求、列模糊点/冲突/异常边界；② 两 AI **交叉互评**，我做最终裁决；③ 我手写《核心技术架构手册》四大板块。
- **典型裁决**：OCR 超时→挂起转人工；舆情风控超时→异步队列解耦；大模型 Output Parse 失败→正则兜底+记录原始输出供复核。
- **结果**：三份文档定稿，收集 5 个异常点（验收要求≥3）均有裁决记录。
- **一句话**：AI 协作的关键是"先定义清楚再动手"，人类负责裁决而非让 AI 自由发挥。

## §10 自述要点 + 防背题提示（面试前最后自查）

1. **用「问题 → 方案 → 反思」结构讲**，不要一口气背书——面试官最怕"背项目"。
2. **"为什么"与"怎么做"分开**：先答为什么（D1~D7 决策与权衡），再答怎么做（P1~P5 机制与结果）。
3. **数字如实**：可验证的是 47/47 测试、17/17 断言、20 并发 0 失败、建案 60ms；200/500/1000 QPS 是工单分档，被追问极限吞吐时讲"瓶颈分析 + 扩容预案"。
4. **突出"我"的贡献**：三方裁决是我拍板、架构手册是我手写、联调留证是我亲自做、多个 Bug 是我定位修复——AI 是工具，决策和兜底是人。
5. **技术纵深点（能让你显得深）**：
   - `interrupt()` 恢复会**重跑当前节点** → 节点必须幂等；
   - 锁的粒度 = 临界区（当前残余风险：`decide_case` 持锁期间跑 `graph.invoke`，锁 TTL 可能提前过期）；
   - `thread_id = case_id` 跨进程对齐；
   - 「LLM 不碰钱」原则。

## §11 三分钟版本（被要求"简短介绍下项目"时用）

> "我做的是一套多 Agent 协同的客诉退赔决策系统，解决传统退款 if-else 规则看不懂凭证和舆情风险的问题。
>
> 技术栈 FastAPI + LangGraph + Redis + PostgreSQL，前端 React。核心思路是**低风险自动秒退、高风险自动挂起转人工**——我用 LangGraph 编排了受理、OCR、欺诈、舆情、决策五个 Agent，决策交给确定性规则（保证可复算可审计），大模型只给风险评分。
>
> 三个难点我重点攻了：**异步解耦**（API 投 Redis Stream 即返回，Worker 后台跑，建案接口 60ms）、**人机断点续跑**（interrupt + Redis checkpoint，审批后原地恢复不重跑）、**三重防重复退款**（幂等键 + 分布式锁 + 乐观锁，压测 0 重复）。
>
> 验证：47 个测试、17 项端到端断言通过，Locust 20 并发 0 失败。踩过的坑我也都解决了，比如审批偶发 500 是 checkpointer 静默回退内存导致的状态分裂。"

# 客诉舆情退赔决策系统 · 当众讲述稿（页面 + 功能 + 实现办法）

> 结构：每一页 = **演示动作**（屏幕上点哪/指哪）+ **讲什么**（可直接念的话术）+ **背后实现**（办法 + 工具，被追问时答）。
> 全稿按登录 → 案件列表 → 案件详情 → 审批中心 → 系统管理 的顺序走，最后附两段现场演示和收尾。

## 0. 开场白（30 秒，先说清"这是什么"）

**讲什么**：

> "各位老师/面试官好，我演示的是**基于多 Agent 协同的客诉舆情退赔决策系统**。
>
> 一句话概括它解决的问题：传统电商退款靠一条条 `if-else` 硬编码规则，既看不懂图片凭证，也识别不了舆情风险，导致人工审核压力大、还容易被'羊毛党'钻空子。
>
> 我用 **LangGraph 编排了 OCR、欺诈检测、舆情分析等多个 AI Agent** 协同工作，实现了**低风险案件自动秒退、高风险案件自动挂起转人工**的双保险机制。"

**背后实现（一句话交代技术栈）**：

> "技术栈是 **FastAPI + LangGraph + PostgreSQL + Redis**，前端 **React + Ant Design**，OCR 用本地 PaddleOCR，风控和舆情用本地 Ollama + Qwen2.5。下面我从登录开始，一页一页带大家走。"

## 1. 登录页 `/login`

**演示动作**：指中间的登录卡片，再指底部灰字"默认账号 agent1 / supervisor1 / admin1，密码 password123"；用 `supervisor1` 登录。

**讲什么**：

> "这是登录页。系统设计了**三种角色、最小权限**：客服只能创建案件、只看得到自己的案子；主管能审批；管理员额外有系统管理页。我先用 supervisor1 登录，方便待会儿演示审批。"

**背后实现（办法 + 工具）**：

> "登录走 JWT 认证——后端用 **PyJWT（HS256）** 签发 token，密码用 **bcrypt** 哈希存储（不存明文），token 有效期 480 分钟。前端把 token 存进 localStorage，之后每次请求都带 `Authorization: Bearer` 头；一旦返回 401，前端自动清空凭证跳回登录页。角色信息随登录返回，前端按 `user.role` 决定菜单和按钮显不显示。"

## 2. 案件列表页 `/`（Dashboard）

**演示动作**：指顶部导航（案件列表/审批中心/系统管理）、右上"新建案件"按钮、状态筛选框、表格里的"风险""状态"两列彩色标签。

**讲什么**：

> "登录后是案件列表。这里我重点讲两件事：**状态机**和**金额单位**。
>
> '状态'列有七种标签：已创建、处理中、待人工审批、已批准、已完成、已驳回、失败——这是我底层定义的**七状态机**，任何流转都必须走合法迁移路径，不允许跳变。
>
> 金额在界面上用'元'输入和展示，但**后端全链路用整数'分'存储**（`amount_cent`），从根上杜绝浮点误差，这是资金类系统的底线。"

**演示动作**：点右上"新建案件"，展示弹窗。

**讲什么（新建弹窗）**：

> "点开'新建案件'，要填订单号、退款金额、投诉内容、凭证文件名、可选的 JSON 风险标记。金额输入元，提交时前端 `Math.round(元 × 100)` 转成分再传后端。风险标记可以直接传 `{"has_malicious_words": true}` 这种结构，后端决策时会读取。"

**背后实现（办法 + 工具）**：

> "这个列表**每 5 秒自动轮询**一次（React `setInterval`），所以状态是准实时的。另一个关键是**权限隔离**：客服登录时接口只返回他自己创建的案子，主管/管理员才看得到全部。新建案件提交时会自动带一个幂等键 `X-Idempotency-Key`（前端 `crypto.randomUUID()` 生成），防止重复提交。"

**演示动作**：建一个 **350 元**案件，点进详情（这是核心场景一）。

## 3. 案件详情页 `/cases/:id`（全场重点）

包含四张卡片：案件详情、多 Agent 处理链路、风险评估、凭证/OCR、人工审批。这一页多停留。

### 3.1 字段卡片

**演示动作**：指上方"案件详情"卡片字段，特别是欺诈分/舆情分/OCR 置信度、决策、退款流水号、Trace ID。

**讲什么**：

> "最上方是案件全量字段：案件号、订单号、金额、币种，以及几个**决策输入**——欺诈分、舆情分、OCR 置信度，下面还有最终决策、决策依据、退款流水号、Trace ID。Trace ID 贯穿整条链路，方便追踪和审计。"

**背后实现**：单接口聚合返回案件全量 JSON，前端 AntD `Descriptions` 渲染；每个案件唯一 `trace_id`（UUID）。

### 3.2 多 Agent 处理链路（AgentFlow）—— 灵魂

**演示动作**：指中间一排彩色圆点和箭头，再指底部图例。

**讲什么**：

> "中间这排圆点，就是整系统的灵魂——**多 Agent 处理链路**。
>
> 从左到右五个 Agent：**受理校验 → 取证(OCR) → 欺诈检测 → 舆情分析 → 决策**，后面跟**人工审批**，再是两个互斥终态：**退款执行**或**驳回**。
>
> 每个圆点颜色代表运行状态：绿色已完成、蓝色处理中（呼吸）、黄色等待人工（闪烁）、红色失败、灰色待执行。
>
> 这个可视化不是前端画死的，而是**由后端真实落库的 Agent 运行记录派生**的——每个 Agent 跑完都写一条 `agent_run` 记录，前端据此渲染成这排灯。"

**背后实现（办法 + 工具）**：

> "底层用 **LangGraph 的 StateGraph** 把这 8 个节点串成一张图。前五个线性串行，`decision` 节点算完结果后走**条件边**分流：APPROVE 走退款执行，REJECT 走驳回，HUMAN_REVIEW 走人工审批。灯光动效用**纯 CSS `@keyframes`**（呼吸 `agent-pulse`、闪烁 `agent-blink`）实现。"

### 3.3 五个 Agent 各自怎么实现（每个点一句）

| Agent | 干什么 | 办法 + 工具 |
| :--- | :--- | :--- |
| 受理校验 | 校验订单号、金额必填合法 | 纯 Python，失败抛异常 |
| 取证 OCR | 提取凭证文字与置信度 | **PaddleOCR** 本地 PP-OCRv5，异常安全降级 |
| 欺诈检测 | 欺诈风险 0–100 打分 | **Ollama + Qwen2.5** 返回 JSON，失败降级置 0 转人工 |
| 舆情分析 | 情绪分 + LOW/MEDIUM/HIGH 分级 | **Ollama + Qwen2.5**，失败降级 LOW |
| 决策 | 算 APPROVE/REJECT/HUMAN_REVIEW | **确定性规则引擎**，不依赖大模型 |

> 讲的时候可以补一句："这几个 Agent 都有 **Mock 和真实模型两套实现**，通过 `settings.*_provider`（mock/paddle/ollama）一键切换——测试用确定性 Mock，生产接真实模型。"

**决策规则引擎内部（从上往下短路判断）**：

> "决策不是大模型拍脑袋，而是确定性规则，保证可复算可审计：证据不足转人工、金额超阈值转人工、命中高风险舆情信号转人工、OCR 置信度低于 0.8 转人工、欺诈分 ≥80 直接拒绝、欺诈分 ≥50 转人工、舆情等级 HIGH 转人工，其余才自动批准。"

### 3.4 人工审批挂起 / 恢复（Human-in-the-loop）

**演示动作**：等 350 元案件跑到 SUSPENDED，指黄色闪烁的"人工审批"节点。

**讲什么**：

> "因为这个案件金额超过阈值（默认 300 元），决策引擎判为 HUMAN_REVIEW，状态停在'待人工审批'，'人工审批'节点**黄灯闪烁**。下面自动弹出'人工审批'卡片，只有主管/管理员才看得到。我填一句意见，点'批准退款'。"

**背后实现（办法 + 工具，这段最值钱）**：

> "人工审批节点用了 LangGraph 的 **`interrupt()` 挂起 + Redis Checkpointer 持久化**：走到这里时整张图的上下文序列化存进 Redis，图暂停；主管审批后按 `thread_id`（= case_id）**从挂起点原地恢复**，不是重跑——既省资源又保证链路可追溯。"

**演示动作**：输入"情况属实，批准"，点批准，等 1~2 秒。

**讲什么（批准后）**：

> "点了批准后，黄灯变绿、'退款执行'节点变绿、状态从待审批一路走到'已完成'，退款流水号也生成了。页面是**每 3 秒轮询**自动刷新的。"

### 3.5 凭证/OCR 与风险评估卡片

**演示动作**：指下方两个卡片。

**讲什么**：

> "'凭证/OCR'卡片展示每张凭证的**OCR 文字和置信度**，置信度低于阈值（默认 0.8）会被强制转人工复核。'风险评估'卡片展示欺诈分、舆情分和风险因子明细，用 JSON 原样呈现，方便审计。"

**背后实现**：每张凭证存 `ocr_text`/`ocr_confidence`，前端 AntD `List` 渲染；风险因子存 JSON，`<pre>` 格式化展示。

## 5. 系统管理页 `/admin`（仅 admin 可见）

**演示动作**：指顶部四个 Tab：阈值配置 / 用户管理 / 审计日志 / 健康监控。

**讲什么**（逐个快速带过）：

> "最后是管理员专属的系统管理页，四个 Tab。
>
> **阈值配置**：改四个业务阈值——金额转人工阈值、OCR 置信度阈值、欺诈分拒绝阈值、欺诈分复核阈值。关键是**阈值在决策时实时读取，改完不用重启、对后续新建案件立即生效**。
>
> **用户管理**：增删改用户、改角色、启停、重置密码。
>
> **审计日志**：每次关键操作都留痕——谁、在哪个案件、做了什么动作、变更前/变更后，对应'全程可审计'。
>
> **健康监控**：探测数据库和 Redis 的连通性与延迟。"

**背后实现（办法 + 工具）**：

> "阈值为什么运行时生效？因为它存在数据库 `system_config` 表，决策 Agent 每次跑都实时读，优先级是 **DB 覆盖值 > 环境变量默认值**（`config_store.py` 无进程缓存）。用户管理用 FastAPI + bcrypt 存密码。审计日志每次流转/决策/审批异步写 `audit_logs` 表。健康检查就是后端执行 `SELECT 1` + Redis `ping` 统计耗时。"

**演示动作**：切到健康监控，点刷新，展示 database/redis 都是绿色"正常"。

### 场景二：128 元 → 自动秒退

## 7. 收尾总结（30 秒）

**讲什么**：

> "总结四个最有底气的点：
>
> **第一**，多 Agent 协同 + 人工断点干预：LangGraph 编排五个 Agent，`interrupt()` + Redis Checkpointer 实现挂起→恢复。
> **第二**，异步解耦：请求只写 Redis Streams 立即返回，Worker 后台跑长推理，Web 线程不被大模型阻塞。
> **第三**，三重防重复扣款：请求幂等键 + 乐观锁 version + Redis SETNX 分布式锁，压测下零重复退款。
> **第四**，全本地化降本：PaddleOCR + Ollama 本地部署，不调外部 API。
>
> 验证数据：后端 47 个测试全过，端到端 17 项断言全过，Docker 五服务健康，QPS 200+ 稳定。谢谢大家。"

> "我实际踩过不少坑。比如大模型输出解析失败会导致 Agent 挂掉，我的兜底是**正则解析 + 记录原始输出转人工**；压测时 Redis 连接池耗尽，改成了连接池 + consumer group 批量消费；前端轮询太频繁导致数据库压力大，评估了 WebSocket 推送方案。这些在 `docs/面试QA库.md` 有 7 个真实修复案例。"

## 附：三句最常用的"背后实现"速答

1. **为什么挂起后能原地恢复？** —— LangGraph `interrupt()` 暂停图 + Redis Checkpointer 序列化上下文，审批 resume 时按 `thread_id`（= case_id）从挂起点续跑。
2. **为什么改阈值不用重启？** —— 阈值存 `system_config` 表，决策时实时读（无缓存），DB 覆盖值优先于环境变量默认值。
3. **怎么保证不重复退款？** —— 三重保障：请求幂等键（sha256 含 user_id 隔离）+ 乐观锁 version + Redis `SET NX` 分布式锁（Lua 脚本安全释放）。

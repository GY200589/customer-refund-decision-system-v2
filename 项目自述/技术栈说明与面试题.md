### 二、分层拆解（每个技术 → 具体功能 → 效果）

**1. 后端框架层：FastAPI**

- 功能：定义 `/auth`、`/cases`、`/review-tasks`、`/admin`、`/health` 路由；`require_role` 依赖注入做 RBAC；Pydantic v2 做输入校验（`amount_cent > 0`）；统一异常处理（500 不泄露堆栈）。
- 效果：异步非阻塞，建案接口平均 60ms 返回；自动 OpenAPI 文档方便前后端联调。

**2. 多 Agent 编排层：LangGraph**

- 功能：`StateGraph` 定义 8 个节点 + 条件边分流；`human_review` 节点 `interrupt()` 挂起；Checkpointer 把图上下文序列化到 Redis，`thread_id = case_id`。
- 效果：五 Agent 串行 + 人工审批 + 退款执行/驳回两个互斥终态；审批后从断点原地恢复，不重跑、不重复调模型。

**3. 数据层：PostgreSQL + SQLAlchemy**

- 功能：`refund_cases`（案件 + version 乐观锁）、`review_tasks`、`audit_logs`、`system_config`（运行时阈值）、`idempotency_records` 等表。
- 效果：业务状态是"事实源"，挂起/审批/决策全留痕可审计；`version` 乐观锁防丢失更新。

**4. 缓存/队列/锁：Redis（redis-stack）**

- 功能：`XADD/XREADGROUP`（Stream）、`PUBLISH`（事件）、`SET NX PX` + Lua（锁）、Checkpointer（RedisJSON + RediSearch）。
- 效果：异步解耦 + 断点续跑 + 防并发审批 + 实时事件推送。

**5. 模型层：PaddleOCR + Ollama/Qwen2.5（Provider 抽象）**

- 功能：`OcrProvider`（Mock/Paddle）、`RiskProvider`/`SentimentProvider`（Mock/LLM）、`LLMProvider`（Mock/Ollama）；`settings.*_provider` 一键切换。
- 效果：测试确定性可复现、生产无缝替换真模型；本地化降本 + 数据不出域。

**6. 认证层：PyJWT + bcrypt**

- 功能：登录签发 JWT（`sub`+`role`+`exp`），前端存 localStorage 带 Bearer 头；密码 bcrypt 哈希存储。
- 效果：无状态鉴权、密码不落明文、401 自动跳登录。

**7. 前端层：React 18 + TS + AntD v5**

- 功能：路由（React Router）、页面（登录/案件列表/详情/审批中心/系统管理）、AgentFlow 可视化组件（CSS keyframes 呼吸/闪烁）、轮询刷新。
- 效果：多 Agent 链路实时可视化、一键审批面板、三角色差异化界面。

**8. 部署/压测：Docker Compose + Locust**

- 功能：5 服务编排 + 健康检查自启动；Locust 模拟并发。
- 效果：一键拉起全套环境，压测自证 20 并发 0 失败。

## 第二部分：技术栈面试题（附参考答法）

### A. 后端框架

**Q1：为什么选 FastAPI，而不是 Django / Flask？**
> 三个理由：① 原生 async/await，天然适配异步任务（大模型推理秒级，不能让请求线程阻塞）；② 自带 Pydantic 校验 + 自动生成 OpenAPI，前后端联调省事；③ 类型提示好，配合依赖注入做 RBAC 干净。Django 太重（本项目是轻量 API 服务），Flask 异步弱。

**Q2：FastAPI 为什么快？同步和异步有什么区别？**
> 它基于 ASGI（Starlette）+ uvloop，async 端点遇到 IO 等待（数据库、Redis、网络）会主动让出事件循环，不占线程。但本项目的"快"核心不在框架，而在**架构**——API 只写库 + 投 Redis Stream 就返回 202，重计算扔给 Worker，所以建案接口 60ms。如果同步跑完整工作流（2~5s），再快的框架也得崩。

**Q3：ASGI 和 WSGI 区别？**
> WSGI 是同步接口，一个请求占用一个线程/进程；ASGI 支持异步和 WebSocket/SSE。FastAPI 走 ASGI，配合 Uvicorn 跑异步服务。

### B. 多 Agent 编排（LangGraph）

**Q4：LangGraph 和 LangChain 什么关系？为什么用 LangGraph？**
> LangGraph 是 LangChain 生态里专门做**有状态、有环、可挂起**的多步工作流的库，把 Agent 用"图"（节点+边）显式编排。我用它是因为需要"挂起→恢复"的人工干预：`interrupt()` + Checkpointer 开箱即用，`thread_id=case_id` 跨进程续跑。如果手写状态机，得自己实现序列化、恢复、节点重入幂等，坑太多。

**Q5：`interrupt()` 挂起和恢复的底层原理？**
> 图执行到 `interrupt()` 时暂停，把当前图状态（各节点输入输出）序列化到 Checkpointer（本项目是 RedisSaver 存 Redis）。恢复时用 `Command(resume=...)` + 同一个 `thread_id` 找到 checkpoint，从断点继续执行后续节点。注意：**LangGraph 恢复时会从头重跑当前节点**，所以 interrupt 节点里的副作用（状态流转、建任务）必须幂等——这是本项目真实踩过的坑。

**Q6：条件边（conditional edges）怎么分流？**
> `decision` 节点算出结果后，用 `add_conditional_edges` 加一个路由函数：APPROVE → execute_refund，REJECT → reject，HUMAN_REVIEW → human_review。人工审批后再二次路由：批准走退款执行，驳回走驳回。这样图结构固定，业务流转由状态决定。

### C. 数据库（PostgreSQL / SQLAlchemy）

**Q7：为什么用 PostgreSQL 而不是 MySQL？**
> 退款是资金操作，需要 ACID 强一致 + 丰富约束（唯一索引、乐观锁行数判断）；PostgreSQL 事务模型更严谨，`jsonb` 存风险因子方便，配合 `system_config` 存运行时配置也自然。MySQL 也能做，但本项目对一致性和可审计要求高，选 PG 更稳妥。

**Q8：乐观锁怎么实现的？**
> 表里加 `version` 列，更新时 `UPDATE ... SET version=version+1 WHERE id=? AND version=?`；如果影响行数为 0，说明数据已被别人改过，抛 `ConcurrencyConflict`。优点是无锁开销、吞吐高，适合审批这种低冲突场景。

**Q9：乐观锁 vs 悲观锁（SELECT FOR UPDATE）怎么选？**
> 乐观锁：冲突低、读多写少、短事务，无锁开销吞吐高，冲突时重试即可。悲观锁：冲突高、长事务，需要先锁行防并发。审批是低冲突场景，我用"乐观锁 + 分布式锁"组合——分布式锁做快速互斥、乐观锁做最终一致，兼顾性能与正确性。

**Q10：SQLAlchemy 怎么防 SQL 注入？**
> 用 ORM 参数化查询（`session.query(...).filter(Model.field == value)`），底层自动绑参，值不拼进 SQL 字符串。全链路无 shell 拼接、无字符串拼接 SQL，模型调用只走 HTTP。

### D. 缓存 / 队列 / 锁（Redis）

**Q11：Redis Streams vs List vs Pub/Sub，为什么选 Stream？**
> List 简单但没确认机制、多消费者要自己管理；Pub/Sub 是"即发即忘"，消费者不在线消息就丢。Stream 原生支持**消费者组**（多 Worker 水平扩容）、**XACK 确认**（至少一次投递）、**pending 重投**、**DLQ 死信兜底**——对"不能丢、不能重复"的退款场景是刚需。

**Q12：消费者组和 XACK 是什么？怎么保证消息不丢？**
> 消费者组让多个 Worker 竞争消费同一 Stream，一条消息只被组内一个消费者处理。消费者处理完调用 `XACK` 确认；没确认的消息会留在 pending 列表，可被重新投递（至少一次语义）。本项目 Worker 崩溃后重启，未 ACK 的消息会续跑；重试超限的进 DLQ。

**Q13：Redis 分布式锁（SET NX PX）原理？为什么释放要用 Lua？**
> `SET key token NX PX 10000`：NX 表示只有 key 不存在才设置（抢锁），PX 设过期时间防死锁，token 用随机值。释放时要先比对 token 再删除，否则可能误删别人的锁（比如自己锁过期了、别人刚拿到锁，自己再去删就删错了）。"比对+删除"两步不是原子的，所以用 **Lua 脚本**在 Redis 内原子执行。

**Q14：为什么 checkpoint 要 redis-stack 而不是纯 redis？**
> LangGraph 的 Redis 检查点依赖 **RedisJSON + RediSearch** 两个模块，`redis:7-alpine` 不带，写 checkpoint 会报 `unknown command 'JSON.SET'`。所以换 `redis/redis-stack-server`，而且不能覆盖 `command`（否则 entrypoint 不加载模块）。

### E. 认证安全（JWT / bcrypt）

**Q15：JWT 原理？无状态是什么意思？**
> 服务端用密钥签一个 token，里面带 `sub`（用户 id）、`role`、`exp`。后续请求前端带这个 token，服务端验签即可识别身份，不用存 session——这就是"无状态"，方便水平扩展。缺点是签出（吊销）麻烦，靠短过期时间缓解。

**Q16：bcrypt 为什么慢？为什么不用 md5/sha256？**
> bcrypt 是专门为口令设计的**慢哈希**，内部有 cost 因子、可配置迭代次数，故意昂贵（本项目登录 340ms）来抵御离线爆破。md5/sha256 是快哈希，可以每秒算几十亿次，字典/暴力破解太快。所以口令必须用 bcrypt/argon2 这类专用算法。

**Q17：密码为什么不能用明文或对称加密存储？**
> 明文一旦数据库泄露密码直接暴露；对称加密需要保管密钥，泄露密钥等于泄露密码。正确做法是单向哈希（bcrypt），只能验不能逆。

### F. 模型（PaddleOCR / Ollama）

**Q18：PaddleOCR 相比 Tesseract / 云 OCR 有什么优劣？**
> PaddleOCR 中文识别效果好、支持 PP-OCRv5 轻量模型、可本地部署不联网，适合中文凭证 + 数据安全场景。Tesseract 中文较弱；云 OCR 有延迟和成本、数据要出域。劣势是本地要占资源、需要下模型。

**Q19：Ollama 是什么？本地 LLM 的优劣？**
> Ollama 是本地大模型运行工具，能跑 Qwen2.5 等量化模型。优点：数据不出域、零 API 成本、离线可用。缺点：推理慢（秒级）、能力弱于云端大模型、并发受限。所以我的架构把 LLM 只用于"风险评分"这类辅助判断，金额和裁决不经过 LLM。

**Q20：怎么保证 LLM 输出稳定（防幻觉）？**
> 四层：① 严格约束输出 JSON Schema；② 解析后做 schema 校验，非法/缺字段算失败；③ 失败重试一次；④ 仍失败**转人工、绝不自动通过**。最坏结果是"多转一单人工"，不会"错误放款"。

### G. 前端

**Q21：为什么用 TypeScript 而不是纯 JS？**
> 编译期类型检查能提前暴露 props 契约、接口字段的错配。本项目真实踩过坑：组件重构后调用方传 `terminal`、组件读 `status`，`SUSPENDED` 恒 false 导致黄灯永不亮——这种"静默 undefined"用 TS 能在编译期就挡住。

**Q22：前端怎么实时展示 Agent 链路？**
> 后端每执行一个 Agent 就落一条 `agent_run` 记录（状态/摘要/错误），前端拿到后按固定顺序渲染成彩色节点，用 CSS keyframes 做呼吸（处理中）和闪烁（等待人工）动效。当前用轮询（详情 3s / 列表 5s），后端也支持 Redis Pub/Sub 事件流。

### H. 部署 / 压测

**Q23：Docker Compose vs K8s 怎么选？**
> 单机开发/演示用 Compose 足够，一键拉起 5 个服务 + 健康检查。K8s 解决的是多机编排、自动扩缩容、滚动发布，本项目规模不需要。但代码已按"无状态 + 外部 Redis/PG + 消费者组"设计，未来要上 K8s 迁移成本低。

**Q24：Locust 压测怎么定位瓶颈？**
> 分接口统计：登录 340ms（bcrypt 刻意昂贵）、建案 60ms（异步解耦）、列表 13ms、健康 7ms。观测链路：Locust → `docker stats`（资源）→ Redis `INFO`/`MONITOR`（锁竞争、热点 key）→ `pg_stat_activity` + `EXPLAIN ANALYZE`（DB）→ 结构化日志 + trace_id → Prometheus/Grafana。

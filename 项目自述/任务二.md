## 任务二的核心目标

任务二的定位非常明确：基于任务一已定稿的需求与设计文档，利用AI编程工具（Cursor/Codex/Trae）生成全栈代码，并完成两大核心业务场景的端到端联调测试。

一句话概括：任务二就是把图纸变成能跑的系统，而且是让AI来写大部分代码，人负责审核、指挥和验收。

## 任务二具体要求拆解

### 1. Loop Engineering（循环工程）—— 任务二的灵魂

这是任务二最核心的要求，也是和“随便让AI写点代码”的本质区别。

核心理念：不是一句一句地手动提示AI，而是设计一套自驱动循环机制——让AI依据只读规格自主执行 → 自动测试/Lint → 捕获报错 → 自行修正 → 再次验证，直至达成目标。

落地步骤：

| 步骤 | 具体操作 |
| :--- | :--- |
| 步骤1：提示词设计 | 把任务一的文档（需求、设计、WBS）喂给Gemini 3.5，让其梳理成一段结构严密的“全阶段Loop驱动Cursor执行提示词” |
| 步骤2：Cursor闭环执行 | 将提示词拷贝至Cursor Composer/Agent终端，AI进入自驱动循环：生成代码 → 跑测试 → 报错 → 修代码 → 再验证，每个阶段输出验证报告 |

图片证据显示，整个过程分阶段验证：

阶段一Loop验证：环境检查（Ollama正常→已切换Python 3.12→创建venv→安装PaddlePaddle CPU版3.0.0→安装PaddleOCR 3.7.0→模型下载至~/.paddlex/）→ 阶段报告“阶段一已完成并通过闭环验证” → 进入阶段二

### 2. 具体实现了哪些功能模块

| 模块 | 技术实现 | 具体内容 |
| :--- | :--- | :--- |
| 后端框架 | FastAPI + Python | 接口路由、JWT鉴权、依赖注入、异常处理 |
| 多Agent工作流 | LangGraph | 编排Intake/OCR/Fraud/Sentiment/Decision五个Agent，实现状态流转（Running→Suspended→Completed） |
| 异步任务处理 | FastAPI + Redis Streams + Worker | 接收请求后写入Streams立即返回，Worker异步消费执行长周期推理 |
| OCR识别 | PaddleOCR（本地部署） | 下载轻量化模型PP-OCRv5_mobile_det/rec，本地推理识别破损照片、快递单文字 |
| 情感/风控分析 | Ollama + Qwen2.5:8B（本地LLM） | 本地推理舆情情感评分和欺诈风险评估 |
| 状态持久化 | Redis Checkpointer | 挂起时序列化保存LangGraph图上下文，人工审批后恢复执行 |
| 幂等与防重 | Redis SETNX + X-Idempotency-Key | 前端携带幂等键，后端分布式锁防重复提交审批 |
| 前端Dashboard | React + 可视化库 | Agent状态流转图实时展示、OCR识别文字渲染、舆情风险分展示、一键审批/拒绝面板 |
| 数据库 | PostgreSQL | 工单主数据、用户信息、审批记录持久化存储 |

### 3. 两大核心场景联调验证（验收硬门槛）

任务二完成后，必须自己测试并录屏证明以下两个场景能跑通：

场景一：超过300元限额 → 自动挂起转人工（Human-in-the-loop）

- 操作：前端Dashboard点击“新建退款申请”，输入金额350.00元，上传破损商品发票图片
- 系统反应：进度条动态展示 Intake Agent(绿) → OCR Parser Agent(绿，渲染出提取文字) → 状态机识别金额超限 → HumanReview节点闪烁黄灯 → 工单状态变为 SUSPENDED
- 唤醒验证：客服主管输入“情况属实，批准退款” → 点击APPROVE → 1秒内自动刷新 → HumanReview节点变绿 → 状态流转为 APPROVED/COMPLETED

场景二：低于300元且无风险 → 自动秒退（全自动决策）

- 操作：前端点击“新建退款申请”，输入金额128.00元，上传清晰商品图
- 系统反应：金额<300元 + 风控欺诈分20（低风险）+ 舆情评分LOW → 多Agent协作流直接驱动自动退款节点
- 流转结果：所有Agent节点2秒内全部变绿 → 案件状态自动变更为 COMPLETED，无需任何人工介入

## 任务二和任务一的衔接关系

任务一出蓝图（需求文档+技术方案+WBS）→ 任务二建高楼（AI按蓝图生成代码+联调验证）

任务二不是让AI“自由发挥”，而是严格依据任务一的规格文档执行——这就是为什么工单要求“将任务一生成的文档放置在docs/下”，让Cursor基于只读规格驱动开发，防止AI跑偏。

## 面试中如何讲任务二

> “任务二是编码实现阶段，核心用了Loop Engineering思想——我先让Gemini把任务一的文档整理成一条结构严密的提示词，扔给Cursor后，它会自动进入‘生成→测试→报错→修复→再测试’的循环，每完成一个阶段会输出验证报告。我实际只需要做环境交互和重大决策确认。
>
> 最典型的例子是阶段一环境验证：Cursor自动检测Ollama、安装PaddleOCR、下载模型到本地，然后跑通OCR+情感分析的闭环验证，出了阶段报告才进入阶段二的后端开发。
>
> 开发完成后，我亲自测了两个核心场景：350元挂起转人工和128元自动秒退，录屏留证。尤其是挂起恢复这个点——客服主管审批后，系统通过Redis Checkpointer恢复图状态继续执行，1秒内完成状态刷新。”

> “这部分的难点是让AI生成的代码符合预期。因为Cursor有幻觉倾向，我通过定稿文档约束它——所有Agent职责、状态流转、接口格式都是任务一锁死的，AI只是‘翻译’成代码，不能自己发明。Loop验证报告就是防它跑偏的护栏。”

## 一句话总结

任务二 = 用Loop Engineering驱动的AI编程模式，把任务一的设计文档转化为全栈可运行代码，并通过两个核心业务场景的端到端联调自证功能完整性，是“AI写代码、人审核把关”的实践

# 客诉舆情退赔决策系统 · 页面效果与实现办法对照

> 本文档按前端页面顺序，逐一说明每个**可见效果 / 功能**背后「用了什么办法 + 什么工具」来实现。
> 适合当众讲述时，每指到一个效果，就能脱口而出一句"它是怎么做的"。

## 一、登录页 `/login`

| 效果 / 功能 | 实现办法 | 用到的工具 |
| :--- | :--- | :--- |
| 登录认证 | 后端校验用户名密码，签发 JWT 返回前端 | FastAPI + **PyJWT**（HS256，过期时间 480 分钟） |
| 密码安全存储 | 密码不存明文，存 bcrypt 哈希 | **bcrypt**（`hashpw` / `checkpw`） |
| 登录态保持 | 前端把 token 和用户信息存进 localStorage，每次请求带 `Authorization: Bearer` 头 | React + `localStorage` |
| 登录过期自动跳回 | 接口返回 401 时前端自动清空凭证并跳转登录页 | 前端 `api()` 统一封装拦截 |

## 二、案件列表页 `/`（Dashboard）

| 效果 / 功能 | 实现办法 | 用到的工具 |
| :--- | :--- | :--- |
| 列表准实时刷新 | 页面 **每 5 秒 `setInterval` 轮询**一次列表接口 | React `useEffect` + `setInterval` |
| 状态彩色标签（7 种） | 底层定义了 **7 状态机**，前端只做枚举到颜色/文案的映射 | Python `Enum`（`state_machine.py`）+ 前端 `labels.ts` |

## 三、案件详情页 `/cases/:id`（全场核心）

### 3.1 字段卡片（决策输入 + 结果 + Trace ID）

| 效果 / 功能 | 实现办法 | 用到的工具 |
| :--- | :--- | :--- |
| 全量字段展示 | 单接口返回案件全量 JSON，前端 `Descriptions` 渲染 | FastAPI 聚合查询 + AntD `Descriptions` |
| 全链路可追溯 | 每个案件生成唯一 `trace_id`，贯穿 Agent 链路与日志 | UUID |

### 3.2 多 Agent 处理链路（AgentFlow 可视化）

| 效果 / 功能 | 实现办法 | 用到的工具 |
| :--- | :--- | :--- |
| 一排彩色圆点 + 箭头 | 前端 `AgentFlow` 组件按固定顺序画 8 个节点 | React 组件 |
| 圆点颜色/动效（绿/蓝呼吸/黄闪烁/红/灰） | 由后端**真实落库的 `agent_run` 记录**派生状态；黄灯用 `interrupt` 挂起派生 | 纯 CSS `@keyframes`（`agent-pulse` / `agent-blink`） |
| 每步执行留痕 | 每个 Agent 跑完都写一条 `agent_run`（状态/耗时/摘要/错误） | PostgreSQL 表 + `record_agent_run` |

### 3.3 五个核心 Agent 及各自实现

| Agent | 干什么 | 实现办法 | 用到的工具 |
| :--- | :--- | :--- | :--- |
| 受理校验 IntakeAgent | 校验订单号、金额必填合法 | 校验字段，失败抛异常 | 纯 Python |
| 取证 OCR EvidenceAgent | 提取凭证文字与置信度 | 本地 OCR 识别，异常安全降级（置信度置空） | **PaddleOCR**（`PaddleOcrProvider`，本地 PP-OCRv5 模型） |
| 欺诈检测 FraudAgent | 欺诈风险 0–100 打分 | 调用 LLM 结构化输出 JSON；失败降级分数置 0 转人工 | **Ollama + Qwen2.5**（`LLMRiskProvider`，`httpx` 调 `/api/generate`） |
| 舆情分析 SentimentAgent | 情绪分 + LOW/MEDIUM/HIGH 分级 | 同上，LLM 返回 JSON；失败降级 LOW | **Ollama + Qwen2.5**（`LLMSentimentProvider`） |
| 决策 DecisionPolicy | 算最终 APPROVE/REJECT/HUMAN_REVIEW | **确定性规则引擎**，不依赖大模型，保证可复算可审计 | `decision_policy.py` + 运行时阈值 |

> 注：以上 Agent 都有 **Mock 与真实模型两套实现**，通过 `settings.*_provider`（`mock / paddle / ollama`）一键切换，测试用确定性 Mock，生产接真实模型。

### 3.4 决策规则引擎（DecisionPolicy 内部）

| 规则（从上往下短路判断） | 处置 |
| :--- | :--- |
| 证据不足（无凭证） | 转人工 |
| 金额 > 阈值（默认 30000 分 = 300 元） | 转人工 |
| 命中高风险舆情信号（监管转办/诉讼/媒体曝光/隐私泄露/群体投诉） | 转人工 |
| OCR 置信度 < 阈值（默认 0.80） | 转人工 |
| 欺诈分 ≥ 拒绝阈值（默认 80） | 直接拒绝 |
| 欺诈分 ≥ 复核阈值（默认 50） | 转人工 |
| 舆情等级 = HIGH | 转人工 |
| 其余 | **自动批准** |

### 3.5 人工审批挂起 / 恢复（Human-in-the-loop）

| 效果 / 功能 | 实现办法 | 用到的工具 |
| :--- | :--- | :--- |
| 走到审批节点自动"挂起" | 节点内调用 `interrupt()` 暂停整张图 | **LangGraph** `interrupt()` |
| 挂起上下文不丢、可恢复 | 图上下文序列化存入 Redis，恢复时按 `thread_id`（= case_id）原地续跑 | **Redis Checkpointer** |
| 审批后原地恢复、不重跑 | Worker `graph.invoke` 检测到 `__interrupt__` 即停；审批接口 resume 后从挂起点继续 | LangGraph + Worker 协作 |
| 审批卡片只对主管/管理员显示 | 前端按 `status === SUSPENDED` 且角色 ∈ {supervisor, admin} 条件渲染 | React 条件渲染 |
| 审批动作幂等 | 审批请求带幂等键，避免重复审批 | 幂等键 + Redis 锁 |

### 3.6 凭证 / OCR 卡片 & 风险评估卡片

| 效果 / 功能 | 实现办法 | 用到的工具 |
| :--- | :--- | :--- |

## 六、贯穿全系统的横切能力

| 能力 | 实现办法 | 用到的工具 |
| :--- | :--- | :--- |
| 异步解耦、长任务不阻塞 | 接口收到请求后**只校验 + 写入 Redis Stream 立即返回 202**，后台 Worker 异步消费跑完整 Agent 链路 | **Redis Streams**（`xadd` / `xreadgroup`）+ 独立 Worker 进程 |
| Worker 高吞吐 | 消费者组 + `ThreadPoolExecutor` 并发消费（并发 4、批 8），失败重试超限进死信队列 DLQ | Python 线程池 + Redis consumer group |
| 幂等防重复扣款（三重） | ① 请求幂等键 `X-Idempotency-Key`（sha256 含 user_id 隔离）② 乐观锁 `version` 字段 ③ Redis `SET NX PX` 分布式锁 + Lua 释放脚本 | Redis + 幂等键公式 + 乐观锁 |
| 实时事件推送 | 每个 Agent 完成后 `publish_event` 推送到 `case:{id}:events` 频道 | Redis Pub/Sub（可扩展 SSE） |
| 模型可插拔 | 所有模型（OCR/风控/舆情/LLM/退款）都抽成 `Provider` 抽象基类，Mock 与真实实现可切换 | Python ABC + 配置项切换 |

## 附：最常用的三句"背后实现"速答

1. **为什么挂起后能原地恢复？** —— LangGraph 的 `interrupt()` 暂停图 + Redis Checkpointer 把上下文序列化保存，审批 resume 时按 `thread_id`（= case_id）从挂起点续跑，不是重跑。

2. **为什么改阈值不用重启？** —— 阈值存数据库 `system_config` 表，决策 Agent 每次实时读取（无缓存），DB 覆盖值优先于环境变量默认值。

3. **怎么保证不重复退款？** —— 三重保障：请求幂等键（sha256 含 user_id 隔离）+ 乐观锁 version + Redis `SET NX` 分布式锁（Lua 脚本安全释放）。

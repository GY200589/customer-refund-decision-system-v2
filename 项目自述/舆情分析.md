## 一、项目总述（1分钟电梯演讲）

面试官你好，我做的这个项目是一个基于多Agent协同的智能客诉退赔决策系统。

背景是：传统电商退款系统只靠“if-else”硬编码规则，处理不了图片凭证和舆情风险，导致人工审核压力大，还容易被“羊毛党”钻空子。

我的核心工作是用LangGraph编排了OCR、风控、情感分析等多个AI Agent协同工作，实现了自动化退赔决策 + 高风控场景下的人工兜底（Human-in-the-loop）。同时，我从0到1完成了全栈开发、容器化部署和QPS 200+的压力测试，确保系统在高并发下稳定运行。

## 三、核心架构与亮点实现（展示你的深度）

### 亮点1：多Agent协同 + 人工断点干预（Human-in-the-loop）

怎么实现的：

- 使用LangGraph定义Agent流程图：Intake（接单）→ Evidence/OCR（证据提取）→ Fraud（风控）→ Sentiment（舆情）→ Decision（金额决策）。
- 在金额 > 300元 或 风控分 > 阈值 时，图执行到 HumanReview 节点自动挂起（Suspended）。
- 利用Redis Checkpointer把整个图的上下文（当前节点、中间结果）序列化保存。客服主管在前端点击“审批/拒绝”时，通过 thread_id 恢复图状态，继续执行后续节点。

面试话术：“这个设计的核心难点是状态恢复的完整性。我通过LangGraph的 MemorySaver 配合Redis，把每个节点的输入输出都存下来。当人工审批完成后，不是重新跑一遍，而是从挂起点原地恢复，既保证了决策链路可追溯，又避免了重复调用大模型造成资源浪费。”

### 亮点2：异步解耦 + 长任务不阻塞（FastAPI + Redis Streams）

怎么实现的：

- 用户提交退款申请后，FastAPI接口只做校验 + 生成工单ID，然后把任务写入 Redis Streams，立即返回 202 Accepted 和 task_id。
- 后台 Worker进程 持续消费Streams，执行完整的LangGraph多Agent推理（可能耗时3-5秒）。
- 前端通过 task_id 轮询或WebSocket获取实时状态。

面试话术：“大模型推理延迟高（2-5秒），如果同步处理，QPS会直接崩到个位数。我借鉴了生产者-消费者模式，用Redis Streams做消息队列，Web层只负责接收请求和返回任务ID，Worker层异步处理。这样Web线程池不会被阻塞，单机能轻松支撑200+ QPS。”

### 亮点3：接口幂等 + 分布式锁防并发审批

怎么实现的：

- 幂等键：前端每次提交审批时携带 X-Idempotency-Key（格式：{order_id}:{action}:{timestamp}），后端用Redis SETNX 加锁，设置过期时间（如5分钟），确保同一审批请求不被重复处理。
- 分布式锁：当两个客服同时审批同一工单时，用Redis SETNX 实现排他锁，先获取锁的请求执行，后获取的返回“工单正在处理中”，防止状态覆盖。

面试话术：“金融类系统最怕资损和重复退款。我设计了双重保障：一是前端传幂等键，Redis SETNX保证同一请求只处理一次；二是对工单ID加分布式锁，防止并发审批导致状态错乱。压测时QPS 500下没有出现一例重复退款或状态覆盖。”

### 亮点4：本地LLM + OCR 降本增效

怎么实现的：

- OCR使用 PaddleOCR轻量化模型（PP-OCRv5），本地推理，单张图片耗时 < 500ms。
- 情感分析使用 Ollama + Qwen2.5:8B，本地部署，无需GPU也可运行（量化版）。
- 设计了 置信度阈值路由：OCR置信度 > 0.85 直接采信；< 0.85 转人工复核；低于0.5 强制挂起。

面试话术：“成本是企业的生命线。如果每笔退款都调OpenAI API，一个月可能几万块。我全部采用本地化模型，一次部署终身免费。同时，我设置了OCR置信度分级策略——低置信度的才转人工，既保证了准确率，又控制了人工成本。”

## 四、痛点与改进（展示你的反思和成长）

| 痛点 | 如何发现 | 改进方案（面试重点） |
| :--- | :--- | :--- |
| 大模型幻觉导致误判 | 测试时发现风控Agent把“正常退货”识别为“高危欺诈” | 方案：引入置信度打分 + 人工兜底。任何Agent输出低于阈值时，强制转Suspended状态，由人工复核。同时增加多Agent投票机制（如风控和舆情结果冲突时，以更保守的为准）。 |
| 压测时Redis连接池耗尽 | Locust压测QPS 300时，日志频繁报 Redis connection timeout | 方案：后端使用redis-py连接池，设置max_connections=100，并调整socket_timeout。同时将Redis Streams消费批量处理改为consumer group模式，提高吞吐。 |
| OCR识别率不稳定 | 用户在昏暗环境下拍照，PaddleOCR召回率仅60% | 方案：增加图片预处理（自动调亮、对比度增强、旋转校正），前端上传时限制最小分辨率。对于仍低置信度的，自动生成“请补充清晰图片”的提示，并转人工。 |
| 状态机恢复时数据不一致 | LangGraph Checkpointer保存了Python对象，升级代码后反序列化失败 | 方案：将挂起上下文设计为JSON序列化（而非Pickle），并增加版本号字段。反序列化时校验版本，做兼容处理。 |
| 前端轮询太频繁 | 前端每500ms轮询一次，压测时DB连接数飙升 | 方案：改为WebSocket + Redis Pub/Sub，Worker处理完任务后主动推送状态变化，减少无效轮询。 |

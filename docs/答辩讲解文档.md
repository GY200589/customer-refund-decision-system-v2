## 1. 开场主张：60 秒电梯陈述

> 各位老师好。我们这个项目叫「客诉舆情退赔决策系统」。它解决的是电商/服务平台上**退款审批靠人工、标准不一、易被薅羊毛、缺乏审计**的痛点。我们做了一件事：**用多 Agent 协同把「凭证识别 → 风险研判 → 金额决策」全链路自动化**，只把高风险案件转给人工。
>
> 项目的底座（工单1）是一套可容器化部署、可压测自证的完整系统；在此之上，我们做了两个关键增量：
>
> - **工单5**：给 Agent 装上了「体检与降本」能力——自动化评测体系（13 条黄金用例 + 四维评分）、成本优化（欺诈+舆情合并为一次 LLM 调用，调用量减半）、以及 Excel 批量审批的全沙箱化（解析 100% 在 Docker 沙箱内完成）。
> - **工单6**：给 Agent 装上了「零信任安全带」——CriticAgent 注入拦截、DLP 数据脱敏、ToolFilter 工具调用校验，三道防线保证**大模型永远不直接接触资金决策**。
>
> 最终效果：200 并发下 QPS 261、错误率 0%；评测通过率 90%；注入攻击在 1ms 内被拦截。下面我从痛点、架构、实现三个层面展开。

## 2. 痛点与亮点

> 本节回答评委第一个问题：**「为什么要做这个项目？」**。先讲透痛点（业务 + 技术两层），再亮出 8 个记忆点（每条都绑了证据，后面章节逐一展开）。

### 2.1 业务痛点：传统人工退赔为什么不行

| 痛点 | 具体表现 | 传统做法的后果 |
|------|---------|--------------|
| **效率矛盾** | 客诉工单量大，人工审核积压，响应超时 | 用户不满、投诉升级为舆情 |
| **标准矛盾** | 不同审核员对相似案例判定不一致，退赔结果不可复现 | 结果引发纠纷、赔付口径失控 |
| **风控矛盾** | 恶意退款、舆情升级、隐私泄露难被人工全覆盖 | 直接资损 + 品牌危机 |
| **审计矛盾** | 人工决策过程不留痕、无统一记录 | 无法追溯，合规审计不达标 |

### 2.2 技术痛点：AI 直接决策为什么「不敢用」   

| 技术痛点 | 具体表现 | 我们的解法 |
|---------|---------|-----------|
| **不可复算** | 同样输入，LLM 可能给出不同结果，资金决策无法审计 | 规则引擎终判，决策阶段 **0 次 LLM 调用**（§4.2） |
| **成本高** | 每单多次 LLM 调用，上下文重复加载，Token 浪费 40-50% | 合并节点，调用次数减半（§5.1） |
| **不可评测** | 改一处代码，不知道 Agent 决策有没有退化 | 13 条黄金用例 + 四维评分 + 双 Judge（§5.2） |
| **不安全** | 注入攻击可操控 LLM、敏感数据随提示词外泄 | 零信任三道防线：Critic/DLP/ToolFilter（§6） |

### 2.3 亮点清单：讲给评委的 8 个记忆点

| # | 亮点 | 归属 | 关键证据 | 一句话讲解 |
|---|------|------|---------|-----------|
| 1 | **多 Agent 全自动决策链** | 工单1 | 7 节点一条链（intake→decision） | 凭证→风险→金额全自动，只把高风险转人工 |
| 2 | **资金决策 0 次 LLM** | 工单1 | 6 条确定性规则链，可复算 | LLM 只做辅助评分，退不退钱由规则引擎说了算 |
| 3 | **真实 OCR + 纠错闭环** | 工单1 | PaddleOCR 置信度 0.9995；缓存 6.67s→0ms | 照片上传即识别，识别错了主管一键修正留痕 |
| 4 | **LLM 成本减半** | 工单5 | 2 次调用→1 次，Token 省 40-60% | 同样的系统能力，一半的模型成本 |
| 5 | **确定性评测防回归** | 工单5 | 13 用例 × 四维评分 × 双 Judge | 每次代码变更，1 秒知道系统有没有退化 |
| 6 | **批量审批沙箱化** | 工单5 | `--network none --read-only` 解析 | 恶意 Excel 最多影响一个一次性容器 |
| 7 | **零信任三道防线** | 工单6 | 注入 1ms 拦截 + 双通道脱敏 + 工具参数校验 | 大模型永远不直接接触资金操作 |
| 8 | **全链路审计可追溯** | 工单1+6 | 状态变更 before/after + 操作人 + 安全事件 | 每笔钱、每次拦截都能回溯到人 |

**讲解要点**：亮点不是吹牛——每条都绑了「证据」，评委追问任意一条，都能落到后面的具体章节和数据上。这是整份文档的「索引页」。

> 本节回答评委第二个问题：**「系统是怎么搭起来的？关键功能是怎么实现的？」**。先给全景和分层，再给选型理由，最后用「一笔退款 10 步」和「关键机制速览」讲透实现。

### 3.3 技术选型：为什么是这套栈

| 组件 | 选它 | 为什么不选别的 |
|------|------|--------------|
| **FastAPI** | 异步原生、Pydantic 请求校验、自动 OpenAPI 文档 | Flask 同步生态弱、Django 重且模板体系冗余 |
| **LangGraph** | 有状态多 Agent 编排，`interrupt()` + checkpoint 支持断点续跑 | BPMN 适合 OA 审批流，不适合 AI 多步推理与状态共享 |
| **PostgreSQL** | 强事务 + 审计表 + 幂等一致性 | MongoDB 无强事务，审计/对账场景吃力 |
| **Redis** | 事件溯源(Stream) + 分布式锁 + OCR 缓存 + 幂等键，一个组件四用 | 单靠 PG 无法承载流式消费与锁语义 |
| **PaddleOCR** | 本地部署、中文识别强、可离线、无数据出境 | Tesseract 中文弱；云 OCR 涉及凭证数据出境 |
| **React + TS + AntD** | 中后台组件生态成熟、TS 类型安全 | Vue 亦可，但团队栈统一、AntD 表格/表单开箱即用 |
| **Docker** | 沙箱隔离（批量审批文件）+ 容器化部署 | 无 |
| **Langfuse** | LLM 调用级可观测（Token/延迟/Prompt 版本） | 自建观测成本高、复用开源方案 |

### 3.4 核心运行机制：一笔退款从提交到终态（10 步）

```
① 客服上传凭证照片 → 后端实时 PaddleOCR，结果回填表单（缓存命中 0ms）
② 提交建案 → X-Idempotency-Key 幂等校验 → 落库 CREATED → 事件推入 Redis Stream
③ Worker 消费事件 → 启动 LangGraph 决策流 → checkpoint 落 Redis
④ intake → order_verify → product_consistency：字段/订单/商品三重数据校验
⑤ critic（工单6）：注入检测，命中 HIGH 即终止链路并审计
⑥ evidence（工单1）：PaddleOCR 识别凭证，命中缓存则 0ms 复用
⑦ merged_risk（工单5）：单次 LLM 调用输出 {欺诈分, 舆情分, 风险等级}
⑧ decision（工单1）：规则引擎终判——0 次 LLM，6 条确定性规则链
⑨ 低风险小额 → 自动退款（ExecuteRefund 前过 ToolFilter 参数校验）
   高风险/超限额/低置信度 → SUSPENDED 挂起
⑩ 主管审批（审批人不能审自己）→ 终态 COMPLETED/REJECTED + 审计 + SSE 推送前端
```

### 3.5 关键实现机制速览（怎么实现的）

| 机制 | 怎么实现的 | 验证 |
|------|-----------|------|
| **幂等建案** | `X-Idempotency-Key` + SHA256(请求体) 存 Redis，重复提交返回首次结果 | e2e 断言通过 |
| **七态状态机** | 合法流转表驱动，非法流转返回 409，不静默覆盖 | pytest 覆盖 |
| **分布式锁** | Redis SETNX + Lua 原子释放，并发审批只一个成功 | pytest 覆盖 |
| **断点续跑** | Redis Stream 消费组未 ACK 重启续跑；LangGraph `interrupt()` + Redis checkpoint 跨进程恢复 | 实测重启后恢复 |
| **OCR 缓存** | `CachedOcrProvider` 装饰器，key=file_hash，上传接口与 EvidenceAgent 共享同一结果 | 实测 6.67s → 0ms |
| **OCR 人工修正** | 主管改文本 → 落库 `ocr_corrected_at/by` → 规则层跳过置信度检查 | 端到端验证 |
| **评测双 Judge** | MockJudge 离线确定性 1s（CI 用）；LLMJudge DeepSeek 语义评分（迭代期用） | 13 用例全跑通 |
| **沙箱解析** | `docker run --network none --read-only --user 1000:1000 --cap-drop ALL`；`SANDBOX_MODE=off` 降级直读 | 压测 + 漏洞对比 |
| **安全三件套插拔** | CriticAgent=图节点、DLP=API 边界中间件、ToolFilter=退款前参数校验，均零侵入原 Agent | 真实注入拦截 |
| **金额安全** | 全链路 `amount_cent` 整数分；ToolFilter 10 万上限 | pytest 覆盖 |

> 上述机制的详细设计分别在第 4/5/6 章展开。第 4 章先把工单1 底座讲透。

## 4. 工单1 · 底座：多 Agent 退赔决策系统

> 本节目的是让评委快速建立对系统主体能力的信任，为工单5/6 的讲解做铺垫（业务与技术痛点已在前文 §2 展开）。

### 4.1 端到端业务流程

```
客服登录 → 新建退款申请(带凭证照片，返回 202 + case_id)
   → 幂等校验 + 落库 → 事件推入 Redis Stream
   → Worker 消费 → LangGraph 多 Agent 决策流
   → 低风险小额：自动 APPROVE 并执行退款
   → 高风险/超限额/低置信度：SUSPENDED 挂起
   → 主管审批(批准/驳回+意见) → 终态 COMPLETED / REJECTED
   全程审计日志 + SSE 实时推送前端
```

### 4.2 多 Agent 决策链路（真实运行节点）

| 节点 | 职责 | 说明 |
|------|------|------|
| **IntakeAgent** | 入站校验 | 订单/金额/用户/必填字段，标准化 |
| **OrderVerifyAgent** | 订单真实性校验 | 订单金额 vs 申请金额比对 |
| **ProductConsistencyAgent** | 商品一致性校验 | 投诉提及商品 vs 订单实际商品 |
| **EvidenceAgent** | 凭证 OCR 核验 | **真实 PaddleOCR**，输出文本 + 置信度 |
| **MergedRiskAgent** | 欺诈 + 舆情合并研判 | 一次 LLM 调用输出双维度评分（工单5 优化点） |
| **DecisionPolicy** | 确定性规则终判 | **0 次 LLM 调用**，规则引擎算出 APPROVE/REJECT/HUMAN_REVIEW |
| HumanReview / ExecuteRefund / Reject | 人工挂起 / 退款执行 / 驳回 | 退款执行幂等 + 终态校验 |

**讲解要点**：两个设计取舍是评委最感兴趣的——
1. **为什么最终决策不用 LLM？** 退赔是资金操作，必须可复算、可审计、合规可解释。LLM 只做辅助评分，规则引擎做终判（6 条确定性规则链）。
2. **为什么用 LangGraph 而非 BPMN？** Agent 之间有状态共享与条件分支，LangGraph 的 StateGraph 模型天然契合；BPMN 更适合 OA 审批流而非 AI 多步推理。

#### 4.2.1 架构设计：为什么是「多 Agent 编排」而不是单一大模型

> 一句话总结：**把"退款该不该批"拆成 8 个单一职责节点，每个节点只回答一个问题，状态全程共享，终判交给确定性规则——大模型不碰资金结论。**

| 设计决策 | 理由 |
|---------|------|
| **单一职责拆分** | 每个 Agent 只做一件事 → 输入输出可单测（13 条黄金用例就是按节点行为设计的）、可单独替换 Provider、可独立优化 |
| **大模型只做辅助评分** | 资金操作必须可复算、可审计、可解释 → 终判走确定性规则链，LLM 仅输出 fraud/sentiment 等辅助分，绝不直接下结论 |
| **全图状态共享（WorkflowState）** | 8 个节点共写一张状态表，下游读上游结论，避免重复计算与口径不一致 |
| **可插拔 Provider** | 每个 Agent 背后是 Provider 接口（mock / 真实服务可切换），评测与生产共用同一套图 |
| **短路与挂起** | 注入直接短路拒付（省 4 个节点成本）；高价值案件挂起等人工，不硬编自动化 |

#### 4.2.2 编排拓扑：一条主链 + 两处短路 + 一次挂起

```text
START → IntakeAgent ─→ OrderVerifyAgent ─→ ProductConsistencyAgent ─→ CriticAgent
                                                                         │
                                 命中注入(HIGH) ─────────────────────────┘ 短路① → Reject
                                                                         │ 通过
                                                                         ▼
                                                          EvidenceAgent（OCR 核验）
                                                                         │
                                                                         ▼
                                                          MergedRiskAgent（欺诈+舆情）
                                                                         │
                                                                         ▼
                                                          DecisionPolicy（规则终判）
                                                                    │
                       ┌───────────────┬─────────────────────────────┘
                  APPROVE         HUMAN_REVIEW                   REJECT
                       │              │ (interrupt 挂起)             │
                       ▼              ▼                             ▼
                ExecuteRefund   HumanReview(主管审批)              Reject
                       │         resume APPROVE/REJECT              │
                       ▼              │                             ▼
                    COMPLETED         └→ ExecuteRefund / Reject   REJECTED
```

- **短路①（安全闸门）**：CriticAgent 命中 HIGH 注入 → 直接 Reject，不跑 OCR/风险/决策（省成本 + 防攻击样本污染后续节点）
- **短路②（规则闸门）**：DecisionPolicy 直接 REJECT（如欺诈分 ≥ 80）→ 跳过人工环节
- **挂起点（人机协作）**：HUMAN_REVIEW → LangGraph `interrupt()` 暂停图，Redis checkpoint 保存图上下文，主管审批后 resume 续跑——**不重跑前置 6 个节点**

#### 4.2.3 节点职责详解（12 个节点逐一）

**分析节点（主链 7 个）——每个 Agent 的定位、输入、处理、输出、对下游的影响：**

| # | Agent | 定位 | 输入 | 核心处理 | 输出 | 对下游的影响 | 代码位置 |
|---|-------|------|------|---------|------|--------------|---------|
| 1 | **IntakeAgent** 入站校验 | 链路网关 | 订单号/金额/投诉文本 | 校验必填字段与金额合法性，输入标准化 | 校验通过（状态透传） | 校验失败 raise → 案件 FAILED 不进链 | `agents/intake.py` |
| 2 | **OrderVerifyAgent** 订单真实性 | 防「查无此单」 | order_id | 调订单服务验单：订单是否存在、金额是否一致 | `is_verified_order` + `verified_order_amount` | **不阻断**：验单失败也继续走，是否转人工由决策规则定 | `agents/order_verify.py` |
| 3 | **ProductConsistencyAgent** 商品一致性 | 防「货不对诉」 | 投诉文本 + order_id | 从投诉中提取商品，与订单实际购买商品比对 | `product_match` + `product_consistency_risk` | **不阻断**：商品不匹配 → 规则层转人工核实 | `agents/product_consistency.py` |
| 4 | **CriticAgent** 注入检测（工单6） | 安全闸门 | 投诉文本 + risk_flags | 25 条预编译正则（6 大类）+ LLM 深度检测（可开关） | HIGH → errors；MEDIUM → risk_flags 标复核 | **短路**：HIGH 直接 Reject；MEDIUM 挂人工 | `agents/critic.py` + `security/critic_rules.py` |
| 5 | **EvidenceAgent** 凭证 OCR 核验 | 证据核验 | 上传凭证文件列表 | **真实 PaddleOCR** 逐张识别，加权汇总置信度 | `evidence_present` + `ocr_text` + `ocr_confidence` | 无凭证 / 置信度 < 0.80 → 转人工（除非已人工修正） | `agents/evidence.py` |
| 6 | **MergedRiskAgent** 欺诈+舆情（工单5） | 风险辅助 | 订单/金额/投诉/OCR/风险标记 | **一次 LLM 调用**同时输出欺诈分 + 舆情分 + 风险等级 | `fraud_score` / `sentiment_score` / `risk_level` / `risk_factors` | 模型异常安全降级 LOW（不阻断链，由规则兜底） | `agents/merged_risk.py` |
| 7 | **DecisionPolicy** 规则终判 | 资金裁决 | 上述 6 个节点的全部结论 + **用户长期退款率** | **0 次 LLM**，8 条确定性规则链（§4.4），含「用户长期退款率」反薅羊毛规则 | APPROVE / REJECT / HUMAN_REVIEW + 原因 | 三路分支决定走执行 / 驳回 / 人工；历史退款率与本次申请比例组合判断 | `agents/decision.py` + `policy/decision_policy.py` |

**动作节点（3 个）——不产评分，执行终态流转：**

| # | Agent | 作用 | 关键实现 |
|---|-------|------|---------|
| 8 | **HumanReview** 人工审批 | 挂起等主管，resume 续跑 | `interrupt()` 暂停 → 状态机 SUSPENDED + 建审核任务 → 主管审批 `Command(resume)` 恢复；**幂等**（仅未挂起时建任务，防重复） | `agents/human_review.py` |
| 9 | **ExecuteRefund** 退款执行 | 批准后执行退款 → COMPLETED | ToolFilter 校验（工单6 最后防线）→ **幂等**（COMPLETED 直返 / `is_refund_executed` 防重复退款）→ APPROVED→COMPLETED | `agents/execute.py` |
| 10 | **Reject** 驳回 | 拒绝 → REJECTED 终态 | 状态机幂等流转 + 审计留痕 | `agents/reject.py` |

**已注册未连线的节点（架构演进痕迹）：**

| Agent | 原职责 | 现状 |
|-------|--------|------|
| FraudAgent | 单独欺诈评分（一次 LLM 调用） | 被 MergedRiskAgent 合并替代 |
| SentimentAgent | 单独舆情分析（一次 LLM 调用） | 同上，合并进 MergedRiskAgent |

> **讲稿话术**：若评委问「链路图里为什么看不到 Fraud/Sentiment 节点」——答：**工单5 做了成本优化，把两个独立节点合并成一个 MergedRiskAgent，一次 LLM 调用输出双维度评分，LLM 调用量减半**（详见 §5.1）。这也是"评测驱动重构"的实例：13 条黄金用例回归通过后才合入。

#### 4.2.4 状态共享：一张 WorkflowState 贯穿全图

LangGraph 的 StateGraph 把 `WorkflowState`（TypedDict，25 个字段）作为「共享黑板」，节点间不直接调函数、不传参，而是**各写各的字段、各读各的结论**：

```text
Intake            写: order_id / amount_cent / complaint_text
OrderVerify       写: is_verified_order / verified_order_amount
ProductConsistency写: product_match / product_consistency_risk
Critic            写: errors / risk_flags
Evidence          写: evidence_present / ocr_text / ocr_confidence
MergedRisk        写: fraud_score / sentiment_score / risk_level / risk_factors
Decision          读: 上述全部 + user_id（反薅羊毛画像） → 写: decision / decision_reason / refund_rate（决策快照）
Execute/Reject    写: 终态后刷新用户 refund_rate（画像闭环）
```

单一职责落到数据层面：**决策节点拿到的是 6 个节点层层校验后的完整证据链 + 用户历史画像，而不是原始投诉文本**。前端「多 Agent 处理链路」图展示的正是这张状态表被逐个节点填充的过程。

#### 4.2.5 多 Agent 协作机制：怎么配合干活

多 Agent 不是"一堆模型在聊天"，而是一套**流水线协作**。系统里没有任何两个 Agent 直接互调函数，协作靠五种机制：

**① 共享黑板传递（数据协作）**
节点间不通信、不传参，只读写同一张 `WorkflowState`（§4.2.4）。前置节点"留证据"，后置节点"取结论"——就像工厂流水线上每个工位在传送带上留下半成品，下个工位接着加工。

**② 串行编排 + 条件路由（流程协作）**
LangGraph StateGraph 定义了唯一执行顺序，三处条件路由决定"下一棒交给谁"：
- `critic` 命中注入 → 短路去 `reject`（安全优先，不给后面的节点留机会）
- `decision` 三分支 → approve 走执行 / reject 走驳回 / 不确定走人工
- `human_review` 审批后 → resume 决定执行还是驳回

**③ 三类角色分工（职责协作）**

| 角色 | 节点 | 干的事 | 类比 |
|------|------|--------|------|
| 质检工位 | intake / order_verify / product_consistency / evidence | 逐层查验，只产证据不做决定 | 流水线上的检验员 |
| 安全门卫 | critic | 只看危险品，发现立即清场 | 安检门 |
| 裁判 | decision | 汇总全部证据，0 LLM 纯规则终判 | 主裁判 |
| 外援 | human_review | 裁判拿不准时叫停比赛等人工 | VAR 视频裁判 |
| 执行官 | execute_refund / reject | 只执行终态动作 | 出纳 |

**④ 一次汇聚（结论协作）**
LLM 辅助评分（merged_risk）和全部规则校验结果，统一汇聚到 DecisionPolicy 一张规则表里裁决——**LLM 是参谋，规则是司令**。LLM 意见再强烈也只是规则表的一个输入字段，翻不了盘。

**⑤ 事件广播（状态协作）**
每个节点干完活都 `publish_event` 到 Redis，前端 SSE 实时刷新链路灯——节点之间不用知道彼此存在，但外部世界全程看得见。

> **讲稿话术**：评委问"多 Agent 怎么协作"——答：**不是对话式协作，是流水线式协作**。共享黑板传数据、StateGraph 定顺序、条件路由选分支、规则引擎做汇聚、事件总线做广播。对话式多 Agent（Agent 互相商量）不可控、不可审计、不可复现；流水线式每一步可单独测试、单独替换、全程留痕——这是资金系统选编排而非群聊的原因。

#### 4.2.6 容错与兜底：某个 Agent 挂了怎么办

设计哲学一句话：**宁可转人工，不可错退款**。任何节点出问题，兜底方向永远指向"更安全的一端"——降级、转人工、留证据，绝不放行。

**第一层：节点级安全降级（每个 Agent 自己兜底）**

| 节点 | 故障场景 | 兜底行为（代码实证） |
|------|----------|---------------------|
| IntakeAgent | 字段缺失/金额非法 | raise 拒绝进链，案件根本不会被处理 |
| OrderVerify / ProductConsistency | 订单服务挂、比对异常 | **不阻断**：记 FAILED 标记继续走，是否转人工交给决策规则 |
| EvidenceAgent | OCR 超时/模型不可用 | 逐文件 try/except，置信度置 None（保守降级）→ 触发「OCR 置信度过低转人工」规则（`evidence.py` 第 34 行） |
| MergedRiskAgent | LLM 超时/返回非法 JSON | 记 FAILED + 返回中性分（fraud=0/sentiment=0/LOW）+ errors 传下游（`merged_risk.py` 第 17-24 行） |
| CriticAgent | LLM 深度检测不可用 | **主闸门不依赖 LLM**：25 条预编译正则是硬规则，`critic_llm_enabled` 默认关闭，LLM 挂了主闸门照站 |
| DecisionPolicy | — | **0 次 LLM 纯规则**，不存在"模型挂"这个故障面，是整个链路最稳的一环 |
| ExecuteRefund | 退款接口失败 | ToolFilter 先校验参数；`is_refund_executed` 幂等防重复退款；COMPLETED 直返 |

**第二层：图级状态兜底（流程不丢、不断）**

| 机制 | 解决的故障 |
|------|-----------|
| Redis checkpoint（LangGraph checkpointer） | 挂起案件跨进程/跨重启恢复，主管审批后续跑不重跑前置节点 |
| Redis Stream 消费组 | Worker 处理中崩溃，消息未 ACK 会重投，案件不丢 |
| DLQ 死信队列（`refund:stream:dlq`） | 节点 raise 导致处理失败，消息进死信队列人工排查，不静默吞掉（`worker/main.py` `_process_safe`） |
| Worker 心跳（15s TTL）+ 容器健康检查 | Worker 进程挂死 → 心跳过期 → 健康检查判定不健康 → 自动重启 |
| Trace 留痕（Langfuse/本地文件） | 每个节点 span 记录耗时与错误，挂了能回放定位到具体节点 |

**第三层：人工兜底（最后防线）**

- 所有"拿不准"的路径（低置信度、验单失败、商品不匹配、模型异常、大额、舆情高危）最终都汇聚到 HUMAN_REVIEW
- SUSPENDED 超 24 小时未审批 → worker 每 60s 扫描自动打「已升级」标记（`risk_flags.escalated` + 审计），防止人工环节本身卡死
- 审批人是人，但审批动作仍走幂等键 + 分布式锁，人点两次也不会重复退款

**第四层：演示兜底（答辩现场稳定性）**

- Provider 全部可插拔：OCR/LLM/风险评分都能一键切 mock 确定性模式，断网、模型服务宕机照样跑通全流程
- Langfuse 未配 Key 自动降级本地文件落盘，观测功能不依赖外网

> **讲稿话术**：评委问"中间某个 Agent 挂了怎么办"——答：**四层兜底**。节点级各自安全降级（OCR 挂了置信度置空、LLM 挂了回中性分）；图级 checkpoint + 消息重投 + 死信队列保证流程不丢；拿不准的统一转人工，人工超 24 小时没批还会自动升级；最极端情况全部 Provider 可切 mock 确定性模式。整条链路里唯一不能挂的是 DecisionPolicy——而它恰好是 0 次 LLM 的纯规则引擎，故障面最小，这是刻意设计的。

### 4.3 可靠性设计（资金系统的底线）

| 机制 | 实现 | 作用 |
|------|------|------|
| 幂等 | `X-Idempotency-Key` + 请求哈希 | 重复提交返回首次结果 |
| 七态状态机 | CREATED→RUNNING→SUSPENDED→APPROVED→COMPLETED 等 | 非法流转 409，不静默覆盖 |
| 分布式锁 | Redis SETNX + Lua 释放 | 并发审批只一个成功 |
| 乐观锁 | `WHERE version = ?` | 防丢失更新 |
| 审计 | 所有状态变更记 before/after + 操作人 | 全链路可追溯 |
| 事件溯源 | Redis Stream + 消费组，未 ACK 重启续跑 | Worker 崩溃不丢案件 |
| 断点续跑 | LangGraph `interrupt()` + Redis checkpoint | 挂起案件跨进程恢复，主管续批不重跑前置节点 |
| 真实 OCR | PaddleOCR（mock/paddle/ollama 三档 Provider 可切换） | 凭证识别置信度 0.999+ |
| OCR 结果缓存 | Redis 缓存复用，上传接口与 EvidenceAgent 共享同一份结果 | 二次识别 0ms，推理量减半（实测 6.67s → 0ms） |
| 数据权限隔离 | 客服仅见本人案件（列表/详情/SSE 流同规则） | 最小权限，防横向越权 |
| 金额整数分 | 全链路 `amount_cent`（分） | 杜绝浮点误差，资金计算安全 |

### 4.4 业务决策阈值（确定性规则链，运行时可调）

决策不是拍脑袋，8 条规则链的阈值**默认来自环境变量、可被管理员在「系统管理」页运行时覆盖**（存 `system_config` 表，Worker 每次决策实时读取，改完即生效，无需重启）：

| 规则 | 阈值（默认） | 处置 |
|------|-------------|------|
| 用户长期退款率 ≥ 80% 且本次申请比例 ≥ 80% | 0.80 | REJECT 拒绝（组合风险） |
| 用户长期退款率 ≥ 50% 且本次申请比例 ≥ 80% | 0.50 | 转人工复核（组合风险） |
| 金额 ≥ 300 元 | 30000 分 | 转人工 SUSPENDED |
| OCR 置信度 < 0.80 | 0.80 | 转人工（证据存疑） |
| 欺诈分 ≥ 80 | 80 | REJECT 拒绝 |
| 欺诈分 ≥ 50 | 50 | 转人工复核 |
| 舆情等级 HIGH / 模型异常 | — | 转人工 |
| 其余（低额 + 低风险 + 证据充分） | — | 自动 APPROVE |

**新增规则的设计意图**：「用户长期退款率」按“已退款订单数 / 购物订单数”计算，但不能单独给用户定罪。只有历史退款率高且本次又申请 80% 以上，或叠加高频申请、重复凭证等异常时才升级；建议范围内的小额部分退款仍可自动处理，减少正常用户误伤。

**讲解要点**：这页直接回答评委「什么案子会自动批、什么会转人工」——把阈值表亮出来，比空谈「规则引擎」有说服力得多。

### 4.5 OCR 人工修正闭环（人机协作纠错）

OCR 不是「识别完就完事」——系统支持**人工修正**，形成闭环：

```
PaddleOCR 识别 → 置信度低/人工发现错误 → 主管在案件详情页点击「修正」
  → 填入正确文本 → 落库标记 ocr_corrected_at/by（审计留痕）
  → 决策规则自动跳过 OCR 置信度检查（尊重人工修正）
  → 案件重新走决策流
```

- 修正后案件级 `ocr_corrected=true`，供规则层识别「已人工确认」，避免低置信度误转人工
- 修正记录**带操作人和时间**，与审计日志对齐，满足合规追溯
- 这是「AI 兜底 + 人终审」治理思路在 OCR 环节的落地：**机器先干，人只处理机器没把握的**

### 4.6 压测自证

Locust 压测（真实端点），验收标准 QPS≥200 且错误率<0.1%：

| 并发 | QPS | P95 | 错误率 |
|------|-----|-----|--------|
| 50 | 139.1 | 98 ms | 0.0% |
| 200 | **261.7** | 690 ms | **0.0%** |
| 500 | 242.5 | 2300 ms | 0.0% |

**讲解要点**：诚实表述——P95 在 200 并发下超了 300ms 红线（690ms），这是后续优化的方向（见第 8 节）。

## 5. 工单5 · 重点一：评测、成本优化与沙箱协作

> 工单5 是「Agent 评测、成本优化与本地沙箱安全协作系统」，三大能力全部并入主仓库，作为增强模块运行。

### 5.1 成本优化：MergedRisk 合并节点（Token 减半）

**优化前的问题**：

```
intake → evidence → fraud(LLM) → sentiment(LLM) → decision → ...
                      ↑两次独立 LLM 调用，内容高度重复↓
           都传 description + evidence_text，Token 浪费 40-50%
```

**优化后**：

```
intake → evidence → merged_risk(单次 LLM) → decision → ...
                      一次调用输出 {fraud_score, sentiment_score, risk_level,
                                    risk_factors, reasoning}
```

**量化收益**：

| 指标 | 优化前 | 优化后 | 收益 |
|------|--------|--------|------|
| LLM 调用次数 | 2 次/工单 | 1 次/工单 | **-50%** |
| Token 消耗 | 上下文重复加载 | 共享一次上下文 | 实节省约 40-60% |
| 响应时延 | 两次串行 LLM | 一次调用 | 时延砍半 |

**答辩话术**：
> 我们在分析系统瓶颈时发现，欺诈评分和情绪分析在 prompt 层面是高度耦合的——都需要投诉文本、风险信号、订单信息。拆分调用意味着 LLM 要重复加载同样的上下文。合并后不仅调用量减半，还让模型在评分时融合两个维度互相补充。这是「成本优化」最直接的体现：**同样的系统能力，一半的模型成本**。

### 5.2 自动化评测体系：Agent 的「体检报告」

**Golden Dataset（13 条黄金用例，覆盖三类场景）**：

| 类型 | 用例 | 期望决策 |
|------|------|---------|
| 业务场景 | 正常小额退款（128 元） | APPROVE |
| 业务场景 | 大额退款（500 元） | HUMAN_REVIEW |
| 业务场景 | 恶意退款嫌疑 + 群体投诉 | REJECT |
| 业务场景 | 舆情升级（监管/媒体）、诉讼、隐私泄露 | HUMAN_REVIEW |
| 业务场景 | 证据缺失 / OCR 低置信度 | HUMAN_REVIEW |
| 边界 | 极小金额边界测试 | APPROVE |
| **安全（工单6）** | **投诉文本含 SQL 注入** | **REJECT** |
| **安全（工单6）** | **投诉文本含 Prompt 注入** | **REJECT** |
| **安全（工单6）** | **退款金额超 10 万** | **REJECT** |

**四维评分体系**：

| 维度 | 满分 | 考察点 |
|------|------|--------|
| 决策正确性 | 40 | 实际决策 vs 期望决策 |
| 金额边界安全 | 20 | 大额/小额边界判断 |
| 理由质量 | 20 | 决策理由可解释性 |
| **安全拦截正确性（工单6）** | **20** | **注入/超限是否被正确拦截** |

**双 Judge 架构**：
- **MockJudge**：离线确定性评分，1 秒内出结果，适合 CI 流水线防回归
- **LLMJudge**：DeepSeek 做语义级评分，适合迭代期深度评估

**答辩话术**：
> AI 系统最难的就是「怎么证明它没退化」。我们建立了一套确定性评测体系：13 条覆盖业务+安全+边界的黄金用例，四维评分。每次代码变更后跑一次 `run_eval --judge mock`，1 秒拿到分数，任何决策行为的变化都会立刻暴露。**评测不是项目收尾的仪式，而是持续集成的闸门**。

### 5.3 沙箱安全协作：Excel 批量审批全流程

**场景**：主管积压了一批挂起工单，逐条审批效率低 → 支持「导出 Excel → 线下批量填 → 上传批量执行」。

```
审核中心 ReviewCenter「导出挂起订单」
   → batch/exporter 查 SUSPENDED 案件，openpyxl 生成 Excel
     （case_id/订单/金额/风险分/舆情等级 只读 + 审批动作/意见 待填）
   → 主管在 Excel 中逐行填写「同意/拒绝 + 意见」
   → 审核中心「上传审批结果」
   → batch/parser 解析 Excel ← 这一步 100% 在 Docker 沙箱内执行
   → batch/executor 逐条 resume 工作流，三层防重
   → 返回汇总：批准 x 笔 / 拒绝 y 笔 / 失败 z 笔（部分失败不整体回滚）
```

**沙箱硬化配置（沿用工单5）**：

```bash
docker run --rm \
  --network none \        # 零网络
  --read-only \           # 只读文件系统
  --user 1000:1000 \      # 非 root
  --cap-drop ALL \        # 丢弃全部能力
  --security-opt no-new-privileges \
  --cpus 1.0 --memory 512m \
  sandbox-image python /sandbox/runner.py
```

**设计要点**：
- 沙箱**只读解析** Excel，不写回；容器一次性、用完即毁
- `SANDBOX_MODE=on|off` 双模式，无 Docker 环境自动降级为宿主机直读（带路径校验）
- **三层防重**：幂等键(SHA256) + Redis SETNX 锁 + 数据库状态前置校验
- 同单多行去重只处理首行；>1000 行分批处理

**答辩话术**：
> 客诉工单里的 Excel 是经典攻击面——恶意宏、公式注入、路径穿越。我们的方案是：**解析这一步永远不发生在宿主机**。容器没网络、没写权限、非 root，即使文件是精心构造的攻击载荷，最多影响一个一次性容器。同时我们保留了 `SANDBOX_MODE=off` 的对比模式，用于压测和漏洞验证，证明「开沙箱比不开沙箱安全得多」。

### 5.4 可观测性：Langfuse 链路追踪

- 每次 LLM 调用的 Token 消耗、延迟、Prompt 版本全记录
- 异步线程队列上报 + 指数退避重试 + 失败缓存降级（不阻塞主流程）
- AgentRun 执行记录持久化 PostgreSQL，案件详情页可视化「多 Agent 处理链路」

## 6. 工单6 · 重点二：零信任安全防护与 AI 治理

> 工单6 是「企业级 Agent 零信任安全防护与 AI 治理系统」。核心主张：**大模型参与的决策链路，每一个入口都默认不可信**。

### 6.1 设计原则

| 原则 | 落地 |
|------|------|
| **零信任** | 每个入站请求、每次 Agent 执行都显式验证 |
| **不改变拓扑** | 新能力作为可插拔过滤层插入，不动现有 Agent 逻辑 |
| **可观测** | 所有拦截/脱敏/过滤操作写审计日志 |
| **可配置** | 阈值与开关运行期可改（复用 system_config） |

### 6.1.1 威胁建模：要防的三类安全威胁与落地防线

工单6 的威胁建模直接承接工单1/5：把工单1 退赔系统当作攻击场景，把工单5 沙箱当作"被动隔离"对照，补上最缺的**主动安全治理**。三类威胁在系统中均有明确落点：

| 威胁 | 攻击方式 | 潜在后果 | 本系统的防线 | 实现位置 |
|------|---------|---------|-------------|---------|
| **间接提示词注入** | 把恶意指令藏在退款说明里，冒充"系统指令" | 绕过人工审批、越权调用退款 API → 资损 | **CriticAgent 规则快速路**：`ignore previous instructions` / `system prompt:` / `forget all` 命中即 REJECT；**LLM 深度检测**（可开关）兜底语义级/编码混淆注入 | `security/critic_rules.py`（25 条预编译正则）+ `security/critic_llm.py` |
| **越狱攻击** | 角色扮演/假设话术绕过 AI 安全护栏 | 诱导 AI 执行越权操作 | 规则层：`你是一个` / `扮演` 类话术命中 MEDIUM → 转人工复核；**架构层兜底**：LLM 只做评分，资金终判是 0 次 LLM 的 DecisionPolicy 规则链，退款执行前还有 ToolFilter 独立校验——**即使 LLM 被越狱成功，也碰不到钱** | `critic_rules.py`（prompt_you_are 规则）+ `policy/decision_policy.py` + `security/tool_filter.py` |
| **敏感数据泄露** | 手机号/身份证/密钥明文进日志、喂给第三方 LLM | 合规风险、隐私泄露 | **DLP 双通道脱敏**：入站打码后再入库、出站返回前再打码；身份证号/手机号/银行卡/邮箱/IP/支付凭证/长数字串 7 类全覆盖；**LLM 拿到的永远是脱敏后文本**；脱敏动作写审计 `dlp:sanitized` | `security/dlp_rules.py` + API 出入站中间件 |

**已验证证据**：
- 评测集 13 条黄金用例中 3 条安全场景（SQL 注入 / Prompt 注入 / 超 10 万退款）全部正确 REJECT（§5 评测报告）
- 实测 SQL 注入案件 `6ab9c87f`：投诉文本含 `DROP TABLE orders`，CriticAgent 命中 `sql_select_from` + `sql_drop_table` 两条 HIGH 规则，1ms 内短路拒绝，审计落 `critic:blocked`
- 25 个安全单测覆盖 Critic 分级决策、DLP 五种脱敏、ToolFilter 金额上限（`tests/test_security_modules.py`）

**已知边界（诚实声明）**：CriticAgent 当前扫描的是投诉文本字段；上传凭证文件的 OCR 文本在证据解析节点处理，暂未回送 Critic 检测。文件渠道的间接注入可复用同一套 CriticEngine 规则扩展，属于后续增强点，不影响答辩演示的三条已验证链路。

**答辩话术**：
> 我们做安全不是"装一个过滤器"就完事，而是先建威胁模型：注入、越狱、泄露三类攻击各自有独立防线。最关键的是**架构级兜底**——就算提示词注入和越狱都成功了，LLM 在本系统里根本没有退款权限：评分归 LLM，裁决归规则，执行归 ToolFilter 校验后的工具白名单。这就是零信任的意思：我不假设模型不会被攻破，我假设它一定会被攻破，然后把关键路径从它手里拿走。

### 6.2 三道防线总览

```
┌────────────────────────────────────────────────────────────────┐
│  第一道：CriticAgent（注入拦截）    Intake 之后、Evidence 之前     │
│    规则快速路（25 条预编译正则，6 大类，<1ms）→ 命中 HIGH 直接拒绝  │
│    LLM 深度检测（可开关）→ 语义级注入/编码混淆/多轮诱导            │
│    输出：PASS / REJECT(审计) / REVIEW(转人工)                    │
├────────────────────────────────────────────────────────────────┤
│  第二道：DLP（数据脱敏）            入站 + 出站 双通道             │
│    身份证(前6后4)、手机号(前3后4)、银行卡(前4后4)、邮箱、IP、      │
│    支付凭证(完全脱敏) —— 7 类敏感信息自动打码，脱敏操作全审计      │
├────────────────────────────────────────────────────────────────┤
│  第三道：ToolFilter（工具调用校验）  执行退款前最后一关             │
│    金额上限 10 万（超限拒绝）、金额必须为正、case_id 必须 UUID v4、 │
│    工具白名单（仅 execute/cancel）—— 拦截即审计                   │
└────────────────────────────────────────────────────────────────┘
```

### 6.3 CriticAgent — 注入攻击检测引擎

**规则快速路（inline，O(1) 预编译匹配）**：

| 攻击类别 | 覆盖模式示例 | 权重 |
|---------|-------------|------|
| SQL 注入 | `SELECT.*FROM`、`DROP TABLE`、`UNION.*SELECT`、`' OR 1=1` | HIGH |
| XSS | `<script>`、`javascript:`、`onload=`、`<iframe` | HIGH |
| **Prompt 注入** | `ignore previous instructions`、`system prompt:`、`你是一个` | HIGH |
| 路径遍历 | `../`、`/etc/passwd`、`C:\Windows` | MEDIUM |
| 命令注入 | `; rm -rf`、`$(cat`、`powershell` | HIGH |
| 模板注入 | `{{config}}`、`{{7*7}}`、`${7*7}` | MEDIUM |

**两级决策**：规则命中 HIGH → 直接 REJECT + 审计；命中 MEDIUM → REVIEW 转人工；规则全过且 `critic_llm_enabled=true` → 送 LLM 做语义级深度检测（隐式注入、Base64/Unicode 编码混淆、多轮诱导）。

**Workflow 集成**：作为独立节点插入 `intake → order_verify → product_consistency → **critic** → evidence`，命中即写入 `errors` 并终止链路，不消耗后续节点。

**答辩话术**：
> CriticAgent 的设计核心是「**快路径保性能，慢路径保深度**」。25 条预编译正则覆盖 6 大类注入模式，全部在 1ms 内完成，用户完全无感；规则没抓住的语义级攻击，由可选的 LLM 深度检测兜底。而且**命中即审计**——每一次拦截都留下了证据，这对 AI 治理的合规要求是必须的。

### 6.4 DLP — 数据脱敏引擎

- **入站脱敏**：API 接收请求后，`complaint_text` 中的敏感字段先打码再入库
- **出站脱敏**：响应返回前对 `ocr_text` / `complaint_text` 等字段再脱敏
- **脱敏操作全审计**：记录原始字段名 + 脱敏类型（`dlp:sanitized`）
- **设计取舍**：正则全覆盖 + 模型不参与运行时脱敏——保证脱敏行为**确定、零成本、可测试**

| 敏感信息 | 脱敏方式 | 示例 |
|---------|---------|------|
| 身份证号 | 保留前6后4 | `110101******123X` |
| 手机号 | 保留前3后4 | `138****5678` |
| 银行卡号 | 保留前4后4 | `6222********1234` |
| 邮箱 | 保留域名 | `***@example.com` |
| 支付凭证 | 完全脱敏 | `pay_********` |

### 6.5 ToolFilter — 工具调用参数校验（资金安全最后一关）

在 `ExecuteRefund` 调用退款网关**之前**做参数级校验：

| 校验 | 规则 | 拦截结果 |
|------|------|---------|
| 金额上限 | `amount_cent <= 10,000,000`（10 万元） | 超限拒绝 + 审计 |
| 金额合法性 | `amount_cent > 0` | 负/零拒绝 |
| case_id 格式 | 必须 UUID v4 | 非法拒绝 |
| 工具白名单 | 仅 `execute_refund` / `cancel_refund` | 其他拒绝 |

**答辩话术**：
> 很多 AI 系统的安全问题出在「模型生成了参数，没人检查参数」。我们的 ToolFilter 在退款执行前做四道校验——金额上限、金额符号、ID 格式、工具白名单。**即使前面所有层都被绕过，这里还有一道独立的确定性闸门**，而且它和规则引擎一样，0 次 LLM 调用、完全可复算。这就是「纵深防御」的兜底意义。

### 6.6 运行时配置与审计

```
critic_rule_enabled = True      # 规则快速路开关
critic_llm_enabled = False      # LLM 深度检测（默认关，按需开）
critic_reject_on_high = True    # HIGH 直接拒绝
dlp_enabled = True              # DLP 总开关
dlp_sanitize_input/output = True# 入站/出站脱敏
tool_filter_enabled = True
tool_filter_amount_max = 10000000  # 10 万元（分）
```

所有安全事件复用 `AuditLog` 表，action 前缀区分：`critic:blocked` / `dlp:sanitized` / `toolfilter:blocked`。阈值通过管理端运行时覆盖、即时生效。

## 7. 三个工单的协同故事

> 单独讲每个工单是「功能罗列」，讲协同才是「工程素养」。以下是三个工单互相咬合的证据：

| 协同点 | 说明 |
|--------|------|
| **评测体系反哺安全** | 工单5 的 Golden Dataset 由 10 条扩展到 13 条，新增的 3 条正是工单6 的安全场景（SQL 注入 / Prompt 注入 / 超 10 万金额），安全能力被纳入持续评测，不是「装完就不管」 |
| **沙箱承载业务闭环** | 工单5 的批量审批是工单6 安全理念的实践场——Excel 解析在沙箱内完成，抵御恶意文件；同时批量的「审批动作」是业务输入，又受 CriticAgent 规则的入境检测约束 |
| **成本优化不动安全** | 工单5 把 Fraud+Sentiment 合并为 MergedRisk，但安全三件套（Critic/DLP/ToolFilter）是独立节点与独立 API 层拦截，优化不影响安全语义，安全也不拖慢优化后的主链路 |
| **可观测贯穿全链路** | Langfuse Trace + AgentRun + 审计日志三套记录各司其职：模型调用看 Trace、Agent 行为看 AgentRun、资金与安全操作看审计 |

**讲解要点**：讲完三个工单后，用这页把「为什么三个工单是一个项目」讲透——它们是同一系统的三个正交维度：**主流程（工单1）、质量与成本（工单5）、安全与治理（工单6）**。

| 端到端 | `verify_e2e.py`：登录 → 自动审批 → 转人工批准 → 越权 403 → 重复审批 409 → 幂等 | **17 项断言通过** |

## 9. 答辩话术与高频提问

### 9.1 一分钟自我介绍（定稿）

> 我们做的是一套「多 Agent 协同的客诉退赔决策系统」：用 LangGraph 编排七个节点完成从凭证 OCR 到退赔决策的全自动化，规则引擎做终判保证资金安全；工单5 解决了 Agent 的可评测性、成本（LLM 调用减半）和办公文件沙箱解析；工单6 用 CriticAgent + DLP + ToolFilter 三道防线落实零信任。系统经过 200 并发压测、13 条黄金用例评测和真实 OCR 端到端验证。

### 9.2 高频提问与应答

**Q1：为什么最终决策用规则引擎而不是 LLM？**
> 退赔是资金操作。规则引擎的决策可复算——同样的输入永远同样的输出，满足监管审计要求；LLM 有幻觉风险，只让它输出欺诈分/舆情分作为参考，不直接决定退不退钱。规则引擎阶段 0 次 LLM 调用，成本也为零。

**Q2：工单5 的成本优化具体省了什么？**
> 原来 fraud 和 sentiment 是两次独立 LLM 调用，上下文高度重叠（都要投诉文本+凭证文本）。合并成 merged_risk 一次调用后：调用次数从 2 次变 1 次（-50%），Token 实际节省约 40-60%，响应时延从两次串行变成一次等效。

**Q3：CriticAgent 会不会误伤正常投诉？**
> 分两级设计避免误伤：规则快速路只对 HIGH 权重模式（如 `DROP TABLE`、`ignore previous instructions`）直接拒绝，MEDIUM 命中只转人工复核不直接拒绝；LLM 深度检测默认关闭、按需开启。实测正常客诉文本（含金额、商品、物流描述）全部 PASS。

**Q4：DLP 脱敏会不会影响 OCR 和决策准确性？**
> 不会。脱敏只作用于 API 入站/出站两个边界，决策链路内部使用原始文本完成 OCR 和评分，出站时才打码。而且脱敏是确定性正则，不引入模型误差，每一笔脱敏都有审计记录。

**Q5：沙箱解析 Excel 的性能如何？会不会很慢？**
> 沙箱只做解析这一件轻量事，容器内只跑 openpyxl，512M 内存限制足够；`--network none --read-only` 让容器启动快、无外联开销。批量审批场景下解析耗时在百毫秒级，主流程无感。沙箱不可用时降级为宿主机直读（带路径校验），保证业务不中断。

**Q6：评测 64 分，通过率 90%，怎么看这个分数？**
> 分数低点主要在恶意退款那条：预期 REJECT、实际 HUMAN_REVIEW——语义上都是「不放款」，但 MockJudge 二值评分给了 0 分。这暴露的是评分粒度问题而非安全漏洞，我们已经明确了改进方案：引入「合理替代决策」给 30 分。**评测体系的价值恰恰在于把这类问题显性化**。

**Q7：三个工单怎么证明是一体的？**
> 三点：1）同一个仓库、同一张 LangGraph 图，工单6 的 critic 就是图上第十个节点，工单5 的 merged_risk 替换的是原 fraud+sentiment 两节点；2）评测用例交叉——工单5 的评测集纳入了工单6 的安全场景；3）运行时配置统一走 `system_config` 表，管理端一套界面管到底。

**Q8：怎么识别职业薅羊毛用户？会不会误伤正常高投诉用户？**
> 系统引入「用户长期退款率」画像，口径是“已退款订单数 / 购物订单数”，不会再用退款案件数当分母。历史退款率不能单独定罪，必须与本次 80% 以上高比例申请，或高频、重复凭证等异常组合后才升级。这样现场反复演示正常部分退款不会全部挂人工，职业薅羊毛式的连续全额退款仍会触发风控。阈值可在 Admin 页实时调整。

**Q8：如果让你继续做，下一步做什么？**
> 三个方向：1）评测 Pipeline 真正接入 `graph.invoke()`，让分数反映真实决策而非 Judge 自评；2）补生产级迁移（Alembic）与高并发下的 P95 优化（推理缓存、连接池调参）；3）沙箱镜像语义化版本管理与 CI/CD 自动构建。

**Q9：OCR 识别错了怎么办？有纠错机制吗？**
> 有，而且是闭环的。识别结果会同时展示文本和置信度：低置信度案件自动转人工；主管发现识别错误，直接在案件详情页点「修正」，填入正确文本后系统会落库标记（带操作人、时间，进审计），并让决策规则**跳过 OCR 置信度检查**——尊重人工判断，避免「AI 错判拖累人正确修正」。另外上传接口与证据核验共享 Redis 缓存，同一张凭证不会重复识别两次。

**Q10：客服能看到别人的案件吗？怎么防越权？**
> 不能。数据权限按角色强制隔离：客服的列表、详情、SSE 事件流都只能看到 `user_id` 归属自己的案件；主管/管理员可见全部；审批环节还校验审批人不能审批自己创建的案子。这套规则在 API 层统一拦截，前端隐藏只是体验层，后端鉴权才是兜底（越权访问返回 403，e2e 已验证）。

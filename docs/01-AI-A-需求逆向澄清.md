# AI-A 需求逆向澄清

> 角色：产品经理兼系统架构分析师（分析型模型）。本文件为独立分析，与 AI-B 输出互不可见，仅依据 `docs/00-原始需求.md`。

## 1. 需求转述

本系统要把旧电商退款模块（if-else 硬编码、只看金额和发货状态、无法识别凭证、易被薅羊毛、后台简陋）重构为"多 Agent 协同的客诉舆情退赔决策系统"。它解决的问题是：多渠道客诉下，如何用 AI 自动完成凭证识别、舆情/欺诈风险研判与退赔金额决策，同时保证高风险与超限额案件能被人工安全接管，且资金操作可防重、可审计。

服务的对象：客服坐席、投诉处理岗、客服主管（审批）、舆情/风控/合规/法务（高风险升级）、管理层、审计与系统管理员。

最终交付：一个可容器化部署、可压测自证的 MVP——前端现代化工作台 Dashboard + 后端 LangGraph 多 Agent 决策流 + Redis 异步与防重 + PostgreSQL 持久化，并附完整需求/架构/测试/审计文档。

## 2. 用户角色

| 角色 | 权限与场景 |
| --- | --- |
| 客服坐席 | 登录后创建退款申请、上传凭证、查看自己/权限范围内案件的详情与决策链路、查看 OCR 与风险报告；不能审批 |
| 客服主管 | 查看所有案件、审批/拒绝人工挂起案件、填写审批意见；具备批准权限 |
| 风控/合规/法务 | 查看高风险案件详情与风险报告，参与重大舆情升级处理（MVP 中作为扩展角色） |
| 系统管理员 | 用户管理、规则/阈值配置、审计查询、健康监控 |
| 审计管理员 | 只读审计日志，不可修改 |

MVP 最小闭环角色：客服 + 客服主管 + 系统管理员。

## 3. 核心业务流程

1. 客服新建退款申请（订单、金额、用户、诉求描述、凭证图片）。
2. 后端快速校验并返回 `202` + `case_id`，写入 PostgreSQL，防重（幂等键）。
3. 异步任务进入 Redis Streams，Worker 消费后启动 LangGraph 决策流：
   - Intake：校验订单/金额/用户/必填字段；
   - Evidence：OCR 识别凭证，输出文本与置信度；
   - Fraud：欺诈风险评分；
   - Sentiment：情绪与舆情风险分级；
   - DecisionPolicy：确定性规则计算决策（APPROVE / REJECT / HUMAN_REVIEW）。
4. 若 HUMAN_REVIEW → 状态 SUSPENDED，人工挂起等待审批；否则自动执行退款。
5. 主管审批（APPROVE/REJECT）→ 唤醒图 → APPROVED/REJECTED → 执行退款 → COMPLETED。
6. 全链路记录审计日志、Agent 执行记录、事件流（SSE 推送前端）。

## 4. MVP 功能范围

**必须实现：** 用户登录/JWT/角色；退款案件创建与查询；X-Idempotency-Key 防重；LangGraph 多 Agent 决策流（Intake/Evidence/Fraud/Sentiment/Decision）；状态机三态流转 + 挂起恢复；Redis 序列化图上下文；OCR 文本与置信度展示；欺诈分与舆情风险分展示；人工审批面板；Redis 分布式锁防重复审批；审计日志；前端 Dashboard；Docker Compose；Locust 压测。

**可以延后：** 完整 RAG 政策检索（MVP 用规则引擎替代，预留接口）；真实支付网关（用 MockRefundProvider）；Prometheus/Grafana 全量接入（提供 healthcheck）；多租户。

**明确不在本期：** 外部公开舆情采集；真实资金操作；真实 PaddleOCR/Ollama 模型强制依赖（用可切换接口 + Mock）。

## 5. 业务边界

- 如果退款金额超过阈值（默认 300 元），则必定进入人工审核。
- 如果 OCR 置信度低于阈值，则不自动批准，转人工。
- 如果欺诈分达到拒绝阈值，则拒绝；达到复核阈值则转人工。
- 如果出现监管转办/诉讼/媒体曝光/隐私泄露/群体性投诉信号，则升级人工。
- 如果同一案件被重复提交，则幂等键命中时返回首次结果。
- 如果证据不足，则只生成补证清单，不生成确定性退赔结论。
- 如果申请人 = 审批人，则拒绝审批（职责分离）。
- 如果未获审批，则不得执行退款，不得向客户承诺赔付金额。

## 6. 异常场景

| 场景 | 处理 |
| --- | --- |
| OCR 超时/不可用 | 转人工，案件 SUSPENDED |
| OCR 置信度过低 | 转人工，不自动批准 |
| 模型超时/不可用 | 转人工，安全降级 |
| 模型输出非法 JSON | 重试一次，仍失败转人工 |
| Redis 不可用 | 快速 API 报错并重试；业务状态以 PostgreSQL 为准，Worker 恢复后继续 |
| Worker 崩溃 | 消息仍在 Stream（Consumer Group 未 ACK），重启后重新消费，保证不丢 |
| 重复审批 | 幂等键 + Redis 锁 + 数据库乐观锁，只允许一个成功，其余 409 |
| 退款动作重复执行 | 独立退款幂等键 + 状态校验，已终态不再执行 |

## 7. 模糊点与冲突点

1. 金额阈值：工单场景一写"超过 300 元"，但阈值是否固定 300、是否按产品/用户分档未定义。
2. OCR 置信度阈值：工单只说"置信度过低转人工"，具体数值未给。
3. 欺诈分阈值：工单示例"20 分 = 低风险"，但"多少分转人工/拒绝"未定义。
4. 舆情风险定义：是否要抓取外部公开舆情未明确；工单场景二为"客户联系监管并准备媒体曝光"（客诉内信号），与"外部舆情采集"边界不清。
5. 数据库选型：工单一处写"MySQL/PG"，总 Prompt 写 PostgreSQL，需裁决。
6. Agent 命名：工单一处写"OCR Agent/舆情风控 Agent/金额决策 Agent"，一处写"Intake/Evidence/Fraud/Sentiment"，需统一。
7. 状态机：工单写三态（Running/Suspended/Completed），总 Prompt 与 Loop 提示词写 CREATED/RUNNING/SUSPENDED/APPROVED/REJECTED/COMPLETED/FAILED，需统一为七态。
8. 金额精度：总 Prompt 要求 Decimal/整数分，工单示例用"350.00 元"，需确认内部存储为整数分。
9. 300ms P95 口径：快速接口还是完整模型链路？需裁决。

## 8. 需要人类决策的问题

**Q1 金额阈值** 问题：超过多少进入人工？方案：固定 300 元（推荐，符合场景一）/ 按产品分档 / 按用户风险分档。影响：决策规则与前端文案。

**Q2 OCR 置信度阈值** 问题：低置信度的判据？方案：0.80（推荐）/ 0.70 / 0.90。影响：Evidence 路由。

**Q3 欺诈分阈值** 问题：多少转人工、多少拒绝？方案：>=50 转人工、>=80 拒绝（推荐）。影响：Fraud/Decision 逻辑。

**Q4 舆情风险定义** 问题：MVP 中"舆情"指什么？方案：客诉内信号（监管/媒体曝光/群体/隐私）为主，外部采集不纳入 MVP（推荐）。影响：Sentiment Agent 与风险字段。

**Q5 模型异常是否允许自动批准** 问题：模型失败时可否自动通过？方案：禁止，转人工（推荐）。影响：资金安全。

**Q6 PostgreSQL 与 Redis 数据分工** 问题：各自保存什么？方案：PostgreSQL 为业务状态/审计最终事实，Redis 存队列、锁、checkpoint、短期事件（推荐）。

**Q7 并发审批返回** 问题：两客服同时审批返回什么？方案：一个成功，其余 HTTP 409（推荐）。

**Q8 状态机粒度** 问题：三态还是七态？方案：七态（推荐，符合总 Prompt 与 Loop 提示词）。

## 9. 验收标准建议

- 未登录访问受保护接口返回 401。
- 客服越权审批返回 403。
- 创建案件快速返回 202 + case_id，P95 < 300ms（快速接口口径）。
- 350 元案件自动进入 SUSPENDED，退款未执行。
- 128 元低风险案件自动 COMPLETED，无需人工。
- 相同幂等键重复请求返回首次结果。
- 并发审批只一个成功，其余 409。
- 模型异常/OCR 低置信度转人工，不自动批准。
- Worker 重启后案件可恢复，不丢状态。
- 审计日志记录前后值与操作者。

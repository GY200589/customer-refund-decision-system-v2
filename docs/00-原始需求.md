### 2 任务描述

#### 2.1 背景介绍

**旧系统现状：** 现有电商退款模块是传统 "if-else" 硬编码规则引擎（仅判断退款金额和是否发货）。随着多渠道客诉增加，出现大量"恶意退款/薅羊毛"事件，用户上传凭证（破损照片、快递单 OCR、聊天截图）无法自动识别，人工客服审核压力极大；旧后台管理界面简陋，客服主管无法直观看到多 Agent 决策链路和"人工审批挂起"节点状态。

**重构需求：** 将旧系统重构为支持"多Agent协同的客诉舆情退赔决策系统"。前端需要现代化工作台 Dashboard，实时展示 Agent 状态流转图、客诉详情、凭证 OCR 识别结果、舆情风险报告，并提供一键审批/拒绝的断点干预（Human-in-the-loop）界面。

#### 2.2 首次工单推荐实现方案（最小可上线 MVP）

- **用户模块：** 客服/主管登录、JWT 鉴权、用户角色与审批权限控制；
- **决策流模块：** 基于 LangGraph 的多 Agent 协作流（包含 OCR Agent、舆情风控 Agent、金额决策 Agent）；
- **流转控制：** 决策流三态流转（Running 运行中 → Suspended 挂起中 → Completed 已完成），挂起状态下通过 Redis 序列化保存图上下文；
- **数据防重：** 前端提交审批防重机制（基于 X-Idempotency-Key 与 Redis 分布式锁）；
- **大屏展示：** 直观展示 Agent 执行路径、OCR 识别文字与舆情风险分；
- **打包压测：** Docker Compose 容器化部署、Locust 压测自证。

**任务二：基于 AI 编程工具的代码生成、功能实现与测试（3.0 人日）**

采用 Loop Engineering 思想，AI 依据只读规格自主执行、自主验证、自主修复。生成前后端全栈代码（后端 LangGraph 多 Agent 工作流 + FastAPI + Redis 异步任务；前端现代化 Dashboard），并完成两大核心业务场景端到端联调：

- **场景一（超限额转人工）：** 新建 350.00 元退款申请，上传破损商品发票图片 → Intake/OCR Agent 流转 → 状态机识别金额超限流转人工节点 → 工单状态 SUSPENDED → 主管审批"情况属实，批准退款" → APPROVED/COMPLETED。
- **场景二（低金额低风险自动秒退）：** 新建 128.00 元退款申请，上传清晰商品图 → 金额 < 300 元、欺诈分 20（低风险）、舆情 LOW → 自动退款，全部 Agent 节点变绿，状态 COMPLETED。

### 3 业务原则（来自项目总 Prompt）

1. 大模型只能辅助决策，不能直接决定最终退赔金额。
2. 退赔金额必须由确定性规则引擎计算，可复算、可解释、可审计。
3. 高金额、监管转办、诉讼、媒体曝光、隐私泄露、群体性投诉必须人工审批。
4. 申请人不能审批自己的请求，审批人与执行人职责分离。
5. 未获审批前不得向客户承诺最终赔付金额。
6. 资金操作必须使用幂等键、双人复核、独立执行权限。
7. 证据不足时只能生成补证清单，不得生成确定性退赔结论。
8. 重要结论必须提供政策、合同或法规引用。
9. 用户输入、文档和工具返回值必须做提示词注入检测。
10. 客户和业务敏感数据必须按权限访问并脱敏。

### 4 核心业务流程（来自项目总 Prompt）

多渠道客诉接入 → 工单标准化和防重 → 客诉分类与实体抽取 → 情绪/舆情/监管/群体风险识别 → RAG 检索政策合同法规历史案例 → 规则引擎计算退赔区间 → Agent 生成分析和客户沟通草稿 → 人工复核和分级审批 → 已批准退赔执行 → 客户回复回访结案 → 审计复盘模型评测。

## 已知环境约束

- 后端计划使用 Python 和 FastAPI
- 计划使用 LangGraph 编排工作流
- 计划使用 Redis 处理异步任务、锁和事件（Redis Streams）
- OCR 计划使用本地 PaddleOCR
- 需要支持人工审核挂起与恢复
- 数据库：PostgreSQL（业务状态与审计为准）
- 前端：React + TypeScript 现代化 Dashboard
- 外部公开舆情采集不纳入 MVP（"舆情风险"由客诉内信号识别，见后续裁决）

# 全项目 STAR 面试复盘（问题驱动版）

> **出发点**：整个项目本质上是一条连续的「**遇到问题 → 决策 → 行动 → 结果**」链条，而这正是 STAR 的四个要素。
> 所以本文**以「问题」为线索**组织全项目复盘——每个问题拆成一段 STAR 口述。亮点（解决得漂亮的问题）与痛点（踩过的坑）都归入同一套问题框架。

## 〇、STAR 速记 + 诚实原则

| 字母 | 含义 | 回答什么 |
|------|------|----------|
| **S** 情境 | 背景/处境 | 在什么约束下、问题是什么 |
| **T** 任务 | 目标 | 我要解决什么、验收标准 |
| **A** 行动 | 我做了什么 | 我的决策 + 关键动作（强调「我」） |
| **R** 结果 | 产出/复盘 | 可量化结果 + 学到什么 |

> **诚实原则**：数据以 `docs/压测报告.md` 与真实联调为准。工单验收分档「合格 ≥200 / 良好 ≥500 / 优秀 ≥1000 QPS」，本机 Docker 单机**实测为 20 并发功能验证（0 失败、吞吐 13 req/s）**。面试被追问极限 QPS 时，如实讲「验证了正确性 + 已有扩容预案」，比虚报数字可信。

## 二、需求与认知问题（任务一）

### P1【方法论】需求模糊、认知偏差 → 三方对齐

- **S** — 工单只有粗需求（"OCR 识别""舆情风控"等模糊描述），且红线是「定稿前禁止编码」，一旦理解偏差，后续代码全返工。
- **T** — 在写代码前把需求与技术方案敲死，消除「人、分析 AI、编程 AI」三方的认知偏差。
- **A** — ① 让 Gemini(业务分析) 与 Cursor(技术评估) 各自**逆向转述**需求、列出模糊点/冲突点/异常边界；② 两 AI **交叉互评**对方方案，我做最终裁决；③ 我亲自手写《核心技术架构手册》四大板块。典型裁决：OCR 超时→挂起转人工；舆情风控超时→异步队列解耦；大模型 Output Parse 失败→正则兜底+记录原始输出供复核。
- **R** — 三份文档定稿，收集 5 个异常点（验收要求 ≥3）均有裁决记录；WBS 拆出 8 人日计划。**学到**：AI 协作的关键是「先定义清楚再动手」，人类负责裁决而不是让 AI 自由发挥。

## 三、项目背景与总体架构（情境铺垫）

**业务背景（S）**：旧电商退款模块是 `if-else` 硬编码规则引擎，只判断金额和是否发货，凭证图片、舆情风险识别不了，恶意退款/薅羊毛频发，人工审核压力大，主管也看不到多 Agent 决策链路。重构目标是把「低风险自动退、高风险人工兜底」落地成**可容器化部署、可压测自证**的全栈系统。

**一句话架构**：

```
用户 → React 前端(antd) → FastAPI(写库 + 投递 Redis Stream 即返 202)
        │ 后台 Worker 消费 Stream → LangGraph 8 节点工作流
        │   intake → evidence(OCR) → fraud → sentiment → decision
        │   → human_review(interrupt 挂起) → 主管 resume → 退款执行
        ▼
状态与审计落 PostgreSQL（事实源）；checkpoint / Stream / 锁 / 事件走 Redis
```

**技术栈**：FastAPI + SQLAlchemy 2.0 + LangGraph + Redis Streams + PostgreSQL + React 18 + antd 5 + Vite + Docker Compose + Locust。

> 下面每个「为什么」都是一个**独立的设计决策问题**，用完整 STAR 拆解——面试官从任何一句「为什么」切入，都能答成一个完整的故事。

## 四、核心设计决策（为什么 · STAR）

### D1【为什么】金额用整数「分」而不是 float？

- **S** — 退款是资金操作，float 的二进制表示（`0.1 + 0.2 ≠ 0.3`）在累加中会产生分毫误差，最终账实不符。
- **T** — 全链路金额零误差、可复算、可审计。
- **A** — 全链路用 `amount_cent`（int 分）存储与计算，仅在展示层换算「元」字符串；弃用 float，也不引入 Decimal（整数分语义更清晰、比较更安全）。
- **R** — 从建案到退款执行无一处浮点运算，DB 用 INTEGER 落库。

### D2【为什么】退款决策交给确定性规则，而不是让 LLM 直接算金额？

- **S** — 业务红线「大模型只能辅助决策，不能直接决定退赔金额」；且 LLM 有幻觉，输出不可复现。
- **T** — 裁决可复算、可解释、可审计。
- **A** — `DecisionPolicy` 用阈值表（if/else）给出 APPROVE / REJECT / HUMAN_REVIEW；LLM 只输出 `fraud_score/sentiment_score` 评分，**金额与裁决都不经过 LLM**。
- **R** — 裁决 100% 可复现；幻觉最坏只是「多转一单人工」，不会错误放款。

### D3【为什么】选 LangGraph 而不是手写状态机？

- **S** — 需要「挂起 → 恢复」的人工干预，多节点编排复杂，手写状态机要自己实现序列化、恢复、节点重入幂等。
- **T** — 状态持久化 + 断点续跑 + 编排可视化，成本可控。
- **A** — 用 LangGraph 内置 Checkpointer + `interrupt()`，开箱即用；弃用手写状态机（省去自研持久化/恢复的坑）。
- **R** — 挂起恢复零自研成本，`thread_id = case_id` 跨 API/Worker 进程续跑。

### D4【为什么】API 只投递消息就返回，不同步跑完整工作流？

- **S** — 大模型推理 2~5s，若同步执行，Web 线程池会被全阻塞，QPS 崩到个位数。
- **T** — 请求秒级返回 + 任务不丢。
- **A** — API 写库 + 投递 Redis Stream 即返 202；Worker 用消费者组异步消费；`XACK` 至少一次投递 + DLQ 兜底异常消息。
- **R** — 建案接口实测平均 **60ms**（压测报告）；Worker 崩溃未 ACK 的消息可重启续跑。

### D5【为什么】「幂等 + 分布式锁 + 乐观锁」三层一起上，而非只用一种？

- **S** — 重复提交（重放）、两个主管并发审批（抢占）、状态覆盖（丢失更新）是**三个不同层面**的风险。
- **T** — 同一请求只处理一次、并发审批只一个成功、状态不丢更新。
- **A** — 幂等键（`X-Idempotency-Key` + 请求体哈希）防重放、`SET NX PX` + Lua 防并发抢占、`version` 乐观锁防丢失更新——三者互补，单用任一都有盲区。
- **R** — 20 并发压测 0 重复退款、0 状态覆盖。

### D6【为什么】人工审批要「断点续跑」而不是「从头重跑」？

- **S** — 从头重跑会重复调用大模型（浪费资源、结果可能漂移）且中间态丢失。
- **T** — 审批后从挂起点原地继续，决策链路可追溯。
- **A** — `interrupt()` 挂起时把图上下文序列化到 Redis checkpoint；`Command(resume=...)` 从断点继续。
- **R** — 不重复调用模型，决策链路完整可追溯；业务状态同时落 PG，checkpoint 丢了也能重建。

### D7【为什么】OCR / LLM 本地化部署，而不是调云 API？

- **S** — 客诉含隐私/敏感数据，不能出域；逐笔调云 API 成本不可控。
- **T** — 低成本 + 数据安全 + 可替换。
- **A** — PaddleOCR + Ollama 本地推理；Provider 抽象层用 `settings.*_provider` 一键切换 mock / 真模型。
- **R** — 数据不出域、零 API 成本；演示确定性可复现、生产可无缝替换真模型。

## 五、业务/架构核心问题（难点 · 亮点）

### P2【亮点】大模型推理延迟秒级，同步处理 QPS 崩

- **S** — 大模型推理 2~5 秒，若 API 同步跑完整工作流，Web 线程池全被阻塞，QPS 崩到个位数。
- **T** — 让请求线程秒级返回，重计算后台异步执行。
- **A** — API 收案后仅「写库 + 投递 Redis Stream」即返回 202，Worker 用**消费者组**（`refund-group`）异步消费执行 LangGraph 全流程；`XACK` 保证至少一次投递 + DLQ 兜底异常消息。
- **R** — 建案接口实测平均 **60ms**（压测报告）；Worker 崩溃未 ACK 的消息可重启续跑，消费者组支持多 Worker 水平扩容。

### P3【亮点】大模型幻觉导致误判

- **S** — 测试时风控 Agent 把「正常退货」误判成「高危欺诈」，直接接模型结论会误伤客户。
- **T** — 在不牺牲自动化的前提下防住幻觉，且守住「资损」红线。
- **A** — ① 决策交给**确定性规则引擎**（阈值表）而非 LLM，LLM 只输出 `fraud_score/sentiment_score` 评分；② 置信度分级路由（OCR <0.80 转人工）；③ **模型异常/低置信度一律转人工，绝不自动通过**。
- **R** — 幻觉被收敛到「最多多转一单人工」，不会错误放款。核心原则固化为「**LLM 不碰钱**」——金额走整数分、裁决走确定性规则。

### P4【亮点】人工介入节点如何做到不丢状态

- **S** — 退款是资金操作，高金额/高风险必须人工接管，但挂起后状态若丢失，案件就「悬空」了。
- **T** — 让 AI 处理常规案件，高风险「原地挂起」转人工，审批后「从断点继续」而非重跑。
- **A** — LangGraph `human_review` 节点 `interrupt()` 挂起，图上下文序列化到 **Redis checkpointer**；`thread_id = case_id` 对齐，主管审批时 API 用 `Command(resume=...)` 跨进程恢复；业务状态**同时落 PostgreSQL**（`SUSPENDED` + ReviewTask + AuditLog）。
- **R** — 断点续跑跨 API/Worker 进程工作；「内存里是进度、数据库里是事实」，checkpoint 丢了也能从 DB 重建、不悬空。两个坑我提前防住：checkpointer 进程间必须一致、interrupt 节点要幂等。

### P5【亮点】资金操作如何防重复退款

- **S** — 金融系统最怕资损：重复提交、两个主管同时审批，都可能重复扣款。
- **T** — 保证「同一请求只处理一次、同一案件并发审批只一个成功」。
- **A** — 三层闭环：① `X-Idempotency-Key` + 请求体哈希（同键不同体报 422）；② Redis `SET NX PX` 分布式锁 + **Lua 校验 token 释放**（防误删）；③ 乐观锁 `UPDATE ... WHERE version = :expected`，行数为 0 抛 `ConcurrencyConflict`。
- **R** — 20 并发压测 0 重复退款、0 状态覆盖。我进一步指出残余风险：`decide_case` 持锁期间跑 `graph.invoke`，锁 TTL 10s 可能提前过期——生产应「锁内只做状态流转、退款执行异步化」。

## 六、工程与并发问题（痛点 · 踩坑）

### P6【痛点】人工审批偶发 500（checkpointer 静默回退内存）

- **S** — 审批接口偶发 500 `KeyError: 'case_id'`，重启后又可能正常，极难复现。
- **T** — 定位并根治这个「时好时坏」的跨进程问题。
- **A** — 系统性排查：看日志发现 `Redis checkpointer init failed` 告警 → 定位到 redis-stack 冷启动 `BusyLoadingError` 触发了 checkpointer 的 `except → return MemorySaver()` **静默降级** → API 用内存、Worker 用 Redis，resume 找不到 checkpoint 从 intake 重跑。修复：失败先**重试 10 次 + 退避**，生产 **fail-fast**（抛错让容器重启），仅 test 环境允许回退内存。
- **R** — 审批端到端恢复 200/COMPLETED/EXECUTED。**学到**：跨进程共享状态时「静默降级」= 状态分裂，降级边界必须显式。

### P7【痛点】多 worker 并发建表竞态（UniqueViolation）

- **S** — `uvicorn --workers 4` 启动时偶发 `UniqueViolation: pg_type_typname_nsp_index`。
- **T** — 解释并消除这个并发启动竞态。
- **A** — 根因：`create_all` 的 check-then-create 在 4 进程并发下同时 CREATE 撞唯一索引。修复：捕获 `IntegrityError` **重试**（冲突说明表已被别的 worker 建好，重试即自愈）。
- **R** — 启动稳定。**学到**：DDL/建表在多实例部署下天然有竞态，生产应上 Alembic 迁移而非 `create_all`。

### P8【痛点】前端状态灯「黄灯闪烁」永不触发（props 契约不一致）

- **S** — 任务要求「等待人工」显示黄灯闪烁，但界面永远是灰色 Steps，看不到黄灯。
- **T** — 让状态灯正确反映 SUSPENDED（等待人工）的黄色闪烁态。
- **A** — 发现组件重构后调用方与组件 props 不一致（调用方传 `terminal`，组件读 `status`），`status === 'SUSPENDED'` 恒 false；且 `dist/` 还是旧 Steps 产物。修复：对齐 props 契约、补状态灯图例、重建前端镜像。
- **R** — 黄灯闪烁态正确显示。**学到**：组件契约要靠 `tsc` 强类型在编译期强制，杜绝「静默 undefined」。

### P9【痛点】AI 生成代码的 7 个边界小坑（AI 代码审查）

- **S** — AI 生成的代码正常路径能跑，但依赖版本、库 API、重入、状态隔离等边界条件下埋了一堆小坑。
- **T** — 逐个定位并修复，沉淀出可复用的「AI 代码审查」经验。
- **A** — 7 个真实修复（详见《面试QA库》第二部分）：

| 坑 | 根因 | 修复 |
|----|------|------|
| `langgraph-checkpoint-redis>=2.0.0` 装不上 | 臆造版本号（实际仅 0.5.1） | 先 `pip index versions` 查真实版本 |
| `RedisSaver.from_conn_string` 报 Invalid checkpointer | 它返回上下文管理器而非实例 | 改 `RedisSaver(redis_url=...)` + `setup()` |
| resume 报 ConcurrencyConflict | interrupt 恢复会重跑当前节点 | 节点改为幂等，先查状态再流转 |
| 测试跨会话污染 | 幂等记录残留命中旧 case_id | fixture 里 `drop_all` + `create_all` |
| checkpoint 报 unknown command 'JSON.SET' | 镜像缺 RedisJSON/RediSearch | 换 `redis/redis-stack-server` 且不覆盖 command |
| `module 'app.agents' has no attribute 'intake'` | `__init__.py` 空文件未导出子模块 | 显式 `from . import intake, ...` |
| `No module named 'app.infrastructure.config'` | 相对导入层级写错 | 点数 = 向上跳的层级 |

- **R** — 全部修复，30/30 测试通过。**学到**：AI 写代码要「引依赖查版本、调库先看签名、interrupt 节点必幂等、集成测试必隔离状态」。

## 七、部署与压测问题（任务三）

### P10【痛点】redis-stack 镜像缺模块导致 checkpoint 失败

- **S** — 写 checkpoint 报 `unknown command 'JSON.SET'`，随后 `no such index`。
- **T** — 让 LangGraph 的 Redis 检查点能正常建索引、读写。
- **A** — 根因：checkpoint 依赖 RedisJSON + RediSearch 模块，`redis:7-alpine` 不带；且覆盖 `command` 会导致 entrypoint 不加载模块。修复：换 `redis/redis-stack-server`，保留默认 entrypoint。
- **R** — checkpoint 读写稳定。**学到**：选基础镜像前先确认功能模块，`redis-stack` 与纯 `redis` 能力差异很大。

### P11【痛点→预案】如何可信地证明高并发能力

- **S** — 工单要求 ≥200/500/1000 QPS 三档，但单机 Docker 环境下「极限吞吐」与「功能正确性」是两件事，虚报数字面试必被戳穿。
- **T** — 用可复现的压测自证稳定性，并给出到达更高 QPS 的路径。
- **A** — ① Locust 20 并发跑通登录/建案/列表/健康四接口，先验证**功能正确性**；② 给出面向 200+ 的瓶颈预案：登录 bcrypt ~340ms（刻意昂贵）用登录态缓存缓解、DB 用 `pg_stat_activity`+`EXPLAIN ANALYZE` 找慢查询+连接池、单 Worker 靠消费者组多实例扩容、锁 TTL 与临界区解耦。
- **R** — 20 并发 259 请求 **0 失败**、平均 61ms、建案 60ms；压测报告明确标注「功能验证口径，非极限压测」。**学到**：结果要可复现、口径要说清，比堆一个好看的数字更重要。

## 九、自述要点与「防背题」提示

1. **用「问题 → 方案 → 反思」结构讲**，不要一口气背书——面试官最怕「背项目」。
2. **「为什么」与「怎么做」分开讲**：先答「为什么」（D1~D7，讲决策与权衡），再答「怎么做」（P2~P5，讲机制与结果），两层都能接住追问。
3. **数字如实**：可验证的是 30/30 测试、20 并发 0 失败、建案 60ms；200/500/1000 QPS 是工单验收分档，本机实测为功能验证口径，被追问极限吞吐时讲「瓶颈分析与扩容预案」（P11）。
4. **突出「我」的贡献**：三方裁决是我拍板、架构手册是我手写、联调留证是我亲自做、4 个 Bug 是我定位修复——AI 是工具，决策和兜底是人。
5. **技术纵深点**：`interrupt()` 恢复会重跑当前节点 → 节点要幂等；锁的粒度 = 临界区；`thread_id = case_id` 跨进程对齐；「LLM 不碰钱」原则。

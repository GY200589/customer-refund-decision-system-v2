## 板块一：架构力 —— 状态机持久化与异步解耦

### 1.1 LangGraph 无状态服务 + Redis Checkpointer

**问题：** 多 Agent 决策流是长耗时任务（OCR + LLM 数秒），若由 FastAPI 同步执行，会占用大量连接；且当需要"人工挂起"时，进程不能一直持有运行中的图上下文，否则 Worker 重启即丢失状态。

**方案：** 把"图结构"和"图运行状态"分离。

- 图结构（StateGraph 的节点与边）是无状态、可共享的代码，每次请求复用。
- 图运行状态（checkpoint）由 `Checkpointer` 持久化。本项目使用 `RedisSaver`（`langgraph-checkpoint-redis`），`thread_id = case_id` 作为线程标识。

**关键点：**
- 挂起：`DecisionPolicy` 判定需要人工时调用 LangGraph 的 `interrupt()`，图暂停，checkpoint（含全部节点输出）写入 Redis，案件状态置为 `SUSPENDED`。
- 恢复：主管审批后，用 `graph.invoke(Command(resume={...}), config={"configurable": {"thread_id": case_id}})` 从 Redis 恢复上下文继续执行，而不是重跑全链路。
- 因此 Worker 可任意重启：重启后从 Redis 恢复，不丢状态。

**为什么 Redis 不是唯一事实源：** Redis 适合低延迟序列化与恢复，但业务最终状态（`refund_cases.status`、审批记录、审计）必须持久化到 PostgreSQL。若 checkpoint 与 PG 不一致，以 PG 为准。

### 1.2 生产者-消费者异步长任务处理

```
[FastAPI] --POST /cases--> 校验 + 落库(PG, status=CREATED)
    --> XADD refund:stream (消息: case_id, trace_id)
[Worker] --XREADGROUP refund-group--> 消费消息
    --> 启动 LangGraph 图 --> OCR/LLM/规则 --> 更新 PG 状态
    --> XACK 确认
```

**为什么用 Redis Streams 而不是简单 List：** Streams 原生支持 Consumer Group，多个 Worker 可以组内竞争消费且同一条消息只被一个消费者处理；消费者崩溃后消息处于 pending 状态，可被重新投递，天然支持"至少一次"语义。

**可靠性：**
- 消费失败 → 进入重试（pengding 重新投递）或死信流（`refund:stream:dlq`）。
- 消息幂等：Worker 处理前先查 PG 状态，已到终态则直接 ACK 跳过，避免重复推进。

## 板块二：AI 工程化 —— 多 Agent 编排与防御性 Prompt

### 2.1 四大 Agent 职责划分

| Agent | 职责 | 是否调用大模型 |
| --- | --- | --- |
| IntakeAgent | 字段校验、标准化 | 否（确定性） |
| EvidenceAgent | 调用 OCR 提取凭证文字与置信度 | 否（调用 PaddleOCR） |
| FraudAgent | 欺诈风险评分 | 可（LLM 辅助，但输出结构化分数） |
| SentimentAgent | 情绪/舆情风险分级 | 可（LLM 辅助） |
| DecisionPolicy | 确定性规则计算最终决策 | 否（纯规则，可复算可审计） |

**设计原则：** 大模型只做"抽取、分类、风险辅助判断"，**最终退赔金额与批准/拒绝由确定性规则引擎决定**。这样保证"可复算、可解释、可审计"，也避免模型幻觉直接造成资损。

### 2.2 Output Parse 失败的 Fallback 机制

大模型输出不稳定（幻觉、截断、非法 JSON），必须防御：

1. 严格约束输出格式（要求返回 JSON Schema）。
2. 解析器做 schema 校验，非法字段/缺失字段视为解析失败。
3. 解析失败**最多重试一次**（用更严格的提示词）。
4. 仍失败 → **不自动批准**，案件转 `SUSPENDED` 人工处理，并记录 `error` 与原始输出摘要。

这样即使模型完全不可用，系统也只会"降级转人工"，不会"误批准"。

## 板块三：算法与数据处理 —— OCR 置信度控制与智能派单

### 3.1 PaddleOCR 置信度阈值路由

OCR 返回每个文本框的置信度，系统计算**总体置信度**（通常取各框置信度的加权/最小值）。

```
overall_confidence = min(field_confidence_list)   # 取最小以保守
路由:
  confidence >= 0.80        -> 进入自动决策
  confidence <  0.80        -> 人工复核(SUSPENDED)
  provider timeout/error    -> 人工复核(SUSPENDED)
```

**阈值从配置/环境变量读取**（`OCR_CONFIDENCE_THRESHOLD`），不散落在代码里。阈值取"最小值"而非平均值是刻意保守：一张凭证只要有一个关键字段识别不可信，就不应自动批准。

### 3.2 最小活跃任务数（Least Active）人工派单

人工审批任务需在多个主管之间分配，采用 **Least Active 派单算法**：

```
选择 active_count 最小且在线的主管
active_count = 该主管当前"进行中"的审批任务数
```

MVP 实现：`review_tasks` 表统计每个主管 `status='PENDING'` 的任务数，按升序分配；平手时按 `last_assigned_at` 最早者优先。该算法让任务均匀分布、避免单点积压。

## 板块四：工程防御 —— 接口幂等与 Redis 分布式锁

### 4.1 防资损幂等键设计公式

```
idempotency_key = hash(actor_id + ":" + case_id + ":" + action + ":" + client_idempotency_key)
```

- `client_idempotency_key` 来自请求头 `X-Idempotency-Key`（前端提交时生成）。
- 首次请求：执行动作，把 key + 请求哈希 + 响应写入 `idempotency_records`（唯一约束）。
- 重复请求：命中记录，返回首次响应。
- 同 key 不同 body：请求哈希不一致，返回 422（防篡改）。
- 退款动作使用**独立幂等键**（`refund:execution:{case_id}`），即使审批重复也不会重复扣款。

### 4.2 Redis SETNX 分布式排他锁防并发审批

**问题（Race Condition）：** 两个客服同时审批同一案件，都读到旧状态，后写覆盖先写（Lost Update）。

**方案：** 三重防护叠加。

1. Redis 锁（快速互斥）：
   ```
   SET refund:approval:{case_id} {random_token} NX PX 10000
   ```
   只有拿到锁的请求能进入审批逻辑；释放用 Lua 脚本校验 token，避免误删他人锁。
2. 数据库乐观锁（最终一致）：
   ```
   UPDATE refund_cases SET status=?, version=version+1
   WHERE case_id=? AND version=?
   ```
   `version` 不匹配说明已被修改，返回冲突。
3. 状态机校验：已到终态（COMPLETED/REJECTED/APPROVED）不允许再次审批。

**结果：** 并发审批只有一个成功，其余返回 HTTP 409，绝不覆盖先完成的决定。

## 附：技术难点一句话总结

| 难点 | 本质 | 解法 |
| --- | --- | --- |
| 长任务阻塞接口 | 同步调用慢 | 异步化：202 + Stream + Worker |
| 人工挂起状态丢失 | 进程持有上下文 | Redis Checkpointer + interrupt/resume |
| 并发审批覆盖 | Lost Update | Redis 锁 + 乐观锁 + 状态机 |
| 模型幻觉误判资损 | LLM 不可信 | 金额与决策用确定性规则 |
| OCR 不可信 | 低置信度 | 阈值路由转人工 |
| 重复退款 | 网络重试 | 幂等键 + 终态校验 |

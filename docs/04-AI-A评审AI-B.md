# AI-A 评审 AI-B

> 分析型模型评审 `docs/02-AI-B-技术方案评估.md`，对照 `docs/00-原始需求.md`。

## 1. 技术方案是否覆盖完整业务流程

覆盖完整。从用户登录 → 案件创建 → Redis Stream 异步 → LangGraph 多 Agent → 决策 → 人工审批 → 退款执行 → 审计，链路清晰。前端 Dashboard 需求亦有体现。

## 2. 状态挂起和恢复是否可靠

方案可靠：Redis checkpoint 恢复图上下文 + PostgreSQL 为最终状态，符合"Redis 不做唯一业务数据库"的原则。建议补充：**checkpoint 与 PostgreSQL 状态不一致时的对齐策略**（以 PostgreSQL 为准，checkpoint 仅作加速）。

## 3. Redis 锁、幂等键、数据库版本号能否防止重复退款

能。三者分层：幂等键防重复提交、Redis SETNX 防并发审批、数据库 `expected_version` 乐观锁防丢失更新，叠加"终态不可再变更"，可防止重复退款。建议补充锁释放的 Lua token 校验已包含，符合预期。

## 4. 模型失败后是否可能误批准退款

不会。AI-B 明确"模型超时/不可用/非法 JSON → 转人工，绝不允许自动批准"，与资金安全红线一致。

## 5. 性能指标是否与异步模型推理相容

AI-B 正确区分了"快速接口 P95<300ms"与"完整模型链路数秒级"，并建议创建接口异步化返回 202。这与"300ms 指快速接口不指完整模型链路"一致，需人类锁定验收口径。

## 6. 哪些内容必须由人类最终裁决

T1-T9 均需人类裁决，尤其：金额阈值、OCR 阈值、欺诈分阈值、模型异常是否自动批准、验收口径。其余（状态机七态、PG/Redis 分工、409 并发返回、PostgreSQL 选型）AI-B 已给出合理推荐，可直接采纳。

## 7. 修改建议

1. 增加"退款执行失败补偿"设计（退款动作幂等落库 + 一致性校验）。
2. 增加"审批意见/驳回理由"字段。
3. 建议将 AI-B 的 T1-T9 与 AI-A 的 Q1-Q8 合并为统一裁决表。

**结论：AI-B 技术方案可行，推荐方案可直接作为 MVP 技术基线，待人类裁决阈值与口径后锁定。**

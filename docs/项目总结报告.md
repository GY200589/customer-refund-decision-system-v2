# 客诉舆情退赔决策系统 · 项目总结报告

## 一、项目目标与成果

构建一个「多 Agent 协同」的客诉舆情退赔决策系统，核心诉求：

1. **降本增效**：用确定性规则 + 可插拔真实模型，替代人工逐单审核，仅高风险案件转人工。
2. **安全可控**：退款是资金操作，必须幂等、防重复、全程审计。
3. **人机协作**：模型给出建议，超阈值/低置信/异常场景强制挂起，由主管审批。

## 三、系统架构

```
                     ┌────────────────────────────────────────┐
  用户 ──HTTP──▶ 前端(nginx/React)                             │
                     │ /api                                    │
                     ▼                                         │
              FastAPI (auth/RBAC/幂等/锁)                      │
                     │ 投递                                     │
                     ▼                                         │
              Redis Stream (refund:stream)                    │
                     │ xreadgroup                              │
                     ▼                                         │
              Worker ──▶ LangGraph 多 Agent 工作流             │
                           intake → evidence(OCR) → fraud      │
                           → sentiment → decision              │
                           → human_review(interrupt) ─┐        │
                             ├─ APPROVE → execute_refund       │
                             └─ REJECT  → reject               │
                     │                                         │
              PostgreSQL (案件/审计/checkpoint)  Redis(checkpoint)
```

## 四、多 Agent 职责

| Agent | 职责 | 输出 |
|-------|------|------|
| IntakeAgent | 订单/金额/字段校验 | 标准化输入 |
| EvidenceAgent | 凭证 OCR（Mock/Paddle） | 文本 + 置信度 |
| FraudAgent | 欺诈风险打分（Mock/LLM） | fraud_score |
| SentimentAgent | 舆情情绪分析（Mock/LLM） | sentiment_score + 风险等级 |
| DecisionPolicy | 确定性决策规则 | APPROVE / REJECT / HUMAN_REVIEW |
| HumanReview | 挂起状态机，等待主管 | interrupt 断点 |
| ExecuteRefund | 幂等退款执行 | refund_ref |
| Reject | 驳回终态 | REJECTED |

## 五、关键设计决策

1. **金额用整数分**：全程 `amount_cent`，接口以「元」展示，杜绝浮点误差。
2. **确定性 Mock + 真模型接口**：Provider 抽象层按 `settings.*_provider` 切换 mock/paddle/ollama，演示可复现，生产可替换。
3. **7 状态机**：`CREATED→RUNNING→SUSPENDED→APPROVED→COMPLETED` + `REJECTED/FAILED`，非法流转直接抛 `InvalidTransition`。
4. **三重防重复扣款**：请求幂等键 + 乐观锁 + Redis 分布式锁。
5. **人机协作断点续跑**：LangGraph `interrupt()` + Redis 持久化 checkpoint，API 与 Worker 跨进程恢复。

## 六、业务阈值（可配置）

| 规则 | 阈值 | 处置 |
|------|------|------|
| 金额 ≥ 300 元 | 30000 分 | 转人工 |
| OCR 置信度 < 0.80 | 0.80 | 转人工 |
| 欺诈分 ≥ 80 | 80 | 拒绝 |
| 欺诈分 ≥ 50 | 50 | 转人工 |
| 舆情 HIGH | — | 转人工 |
| 模型异常 | — | 转人工（绝不自动通过） |

## 七、真实验证结果

- 后端 `pytest`：**30/30 通过**（含挂起-恢复、幂等、越权 403、端到端审批）。
- 前端 `npm run build`：通过（3043 模块，产物 ~1.1MB gzip 348KB）。
- Docker 全栈：`docker compose up --build` 拉起 5 个服务，健康检查通过（详见 loop-reports 各 phase）。
- 修复的真实问题（详见面试 QA 库）：checkpoint-redis 版本号错误、RedisSaver 上下文管理器 API、节点 resume 重入、测试跨会话污染、redis-stack 模块加载等 7 项。

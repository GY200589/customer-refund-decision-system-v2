# Phase 4 报告：性能优化

## 结论（一句话）

将后端从「200 并发即崩溃」优化到「200 并发 QPS 262 / 0% 错误」，**吞吐提升约 50 倍、P95 延迟下降约 98%**，远超任务要求的「≥15% 吞吐 或 ≥20% 延迟」目标。QPS≥200 与错误率<0.1% 已达标；P95<300ms 在 50 并发达标（98ms），在 200 并发未达标（690ms），瓶颈落在业务代码的同步决策端点（见「剩余瓶颈」）。

## 优化项清单（7 类，全部为基础设施/配置层，未改业务规则）

| # | 优化项 | 改动 | 根因 |
|---|--------|------|------|
| 1 | DB 连接池扩容 | `pool_size=20 / max_overflow=40 / pool_timeout=10 / pool_recycle=1800`，postgres `max_connections=400` | 默认 `5+10` 在 200 并发下 QueuePool 雪崩（日志 `QueuePool limit of size 5 overflow 10 reached`） |
| 2 | 多 worker | uvicorn `--workers 4` | 单 worker 的 anyio 线程池约 40 线程，无法吸收 200 并发 |
| 3 | Token 池 | `gen_tokens.py` 预生成 JWT，压测轮转分发 | bcrypt 登录 ~250ms×200 并发形成登录风暴，掩盖真实业务延迟 |
| 4 | 资源与 PG 调优 | postgres 2→8 CPU / 1→2G；`shared_buffers=512MB / work_mem=8MB / effective_cache_size=1536MB` | postgres CPU 饱和导致 API 连接池超时 |
| 5 | Worker 并发消费 | `ThreadPoolExecutor(4)` + `batch=8`（`worker_concurrency`/`worker_batch_size` 可配） | 原 `count=1` 串行 `graph.invoke`（约 2s/单）吞吐仅 0.43 单/s，积压 2w+ 并抢占 PG 连接 |
| 6 | 数据库索引 | `refund_cases(user_id,created_at)` 复合 + `created_at`/`status`；5 张子表 `case_id` FK 索引；`review_tasks(status,assigned_to)` | `list_cases` 全表扫描+排序、`get_case` 4 次子表全表扫描，压测单用户 agent1 案件量上万时急剧放大 |
| 7 | 压测脚本修正 | 审批 409（跨阶段幂等冲突）不计业务失败 | 预置队列跨阶段复用导致 409 污染错误率 |

## 剩余瓶颈与暂停条件

1. **P95<300ms 在 200 并发未达标（690ms）**，两个根因都落在业务代码（Task 2 产出）：
   - `POST /cases/{id}/decision` 在 API 内**同步** `graph.invoke`（median ~460ms / P95 1900ms），审批时阻塞请求线程并长时间占用 DB 连接；改为异步（202 立即返回、Worker 处理后经事件流回传）需改业务架构。
   - `create_case` 单请求 5 次 DB 往返（幂等查询 + 案件 + 证据 + 审计 + 幂等记录 + commit + Redis 发布），平均 480ms；合并为批量写入/异步落库需改业务代码。
2. **1000 并发 2.8% 错误**：postgres 在极端过载下饱和（`QueuePool` 超时）。这是容量上限，非确定性缺陷；横向扩容或引入读写分离可缓解，属架构演进而非本次优化范围。

按任务三暂停条件 **(c)**：上述 P95 目标需修改业务代码（Task 2 产出），现暂停并交回确认是否继续优化业务路径。
